## Framing — why the v1.0.4 §D12 fix wasn't enough

v1.0.4 §D12 replaced `simctl uninstall + install` with an in-place clear:

```
Terminate + PrivacyResetAll + SandboxClearInPlace(via `simctl spawn /bin/rm`) + Launch
```

Rationale at the time: the ReportCrash dialog was diagnosed as triggered by `simctl uninstall` revoking the install receipt while the OS still tracked the running process. Remove the uninstall, dialog should stop.

Insight's 2026-07-11 report says the dialog is STILL firing. Two of the four ops (Terminate + SandboxClearInPlace) can plausibly still trip iOS 26.5's crash-reporter:

- **`Terminate` via `simctl terminate <UDID> <bundle-id>`** sends the target app SIGKILL. `com.apple.ReportCrash` is signalled on any SIGKILL of a tracked process — it treats SIGKILL identically to a "real" abnormal exit unless the killer went through a graceful pathway (launchd stop, XCUITest terminate-with-notify, etc.).
- **`SandboxClearInPlace` via `simctl spawn /bin/rm -rf`** is invoked immediately after Terminate. Even though we terminated first, the sandbox-wipe running while the OS is still finalizing the crash-report intake window can escalate the fake-crash into a dialog.

Contrast with visual/perf gates that DON'T fire the dialog: they use `simctl terminate + simctl launch` with no `rm` between them. So the differentiator is EITHER (a) the rm spawn happening in the window, OR (b) the combination of terminate + privacy-reset + rm being sufficient to reach a heuristic threshold in ReportCrash.

Either way, the v1.0.4 §D12 in-place clear via `simctl` is not sufficient. The systemic answer must move the clear INSIDE the XCUITest runner process, using XCUIApplication + FileManager directly. No `simctl terminate`. No `simctl spawn rm`. No signalling of `com.apple.ReportCrash`.

This is what insight proposed in their 2026-07-10 finding H (unchanged) and now escalates.

## Decisions

### D1 — HARD-REQUIRED — Runner-side `POST /session/reset-app-data` endpoint

Runner exposes a new authenticated endpoint that performs the clear entirely inside the XCUITest test-host process:

```
POST /session/reset-app-data { sessionId }
  → 200 { ok: true, wallMs: N }
  → 404 { error: "unknown session id" }
```

Runner-side handler:

1. Look up the session's cached `XCUIApplication` binding (same as `/session/relaunch-app`).
2. Call `XCUIApplication.terminate()`. This is XCTest's cooperative terminate; it does NOT send SIGKILL and does NOT signal ReportCrash. It uses `testmanagerd`'s "terminate app under test" pathway which is a first-class supported operation.
3. Call `FileManager.default.removeItem(at:)` on each of the app's sandbox subdirectories: `Containers/Data/Application/<data-uuid>/Documents`, `.../Library`, `.../tmp`. Path is resolved by asking the sim's `NSHomeDirectoryForUser` for the target app's home (available via `XCTestCase.testRunner` context inside the runner process because XCUITest has entitlement to inspect other apps' data containers on the sim).
4. Call `XCUIApplication.launch()`. Re-attaches the XCUITest binding cleanly.
5. Return 200 with `wallMs`.

**Fallback if step 3 refuses due to sandbox permissions**: the runner shells out to `simctl spawn <UDID> /bin/rm -rf <resolved-path>`. But crucially, at that moment the app is NOT the "currently-running-and-suddenly-killed" thing — `XCUIApplication.terminate()` in step 2 is the cooperative pathway, ReportCrash was not signalled, so a subsequent `rm` under the container root does not escalate to a dialog. This fallback is what makes the design work even when the FileManager route is closed off; it moves the `simctl` call OUT of the "just killed the target app via SIGKILL" window.

Wire types:

```rust
// smix-runner-wire
#[serde(rename_all = "camelCase")]
pub struct SessionResetAppDataRequest { pub session_id: String }
pub struct SessionResetAppDataResponse { pub ok: bool, pub wall_ms: u64 }
```

Rust client method: `HttpRunnerClient::reset_session_app_data(req) -> SessionResetAppDataResponse`.

### D2 — HARD-REQUIRED — New yaml verb `clearAppData` (insight's alternate ask)

Insight offered to migrate their entire `.devtools/qa/sim/subflows/` corpus in one PR the moment a clean verb ships. Take them up on it:

```yaml
- clearAppData                    # v1.0.8+ verb — no uninstall/install, no dialog
- launchApp: {}                   # (or omit — clearAppData does not launch)
```

Semantics:
- Adapter translates `- clearAppData` to `Session::reset_app_data()` on the current session's target bundle.
- Errors if no session is open — this is a session-scoped op, not a bare simctl.

`launchApp: { clearState: true }` becomes a legacy alias that emits `WARN: launchApp.clearState is deprecated; migrate to \`clearAppData\` — see docs/ai-guide/09-sessions.md`, then internally calls `Session::reset_app_data()` + `XCUIApplication.launch()`. Consumers who don't migrate keep working (no BREAKING change); consumers who migrate see the deprecation go away.

### D3 — HARD-REQUIRED — SDK `Session::reset_app_data()` on all 4 SDKs

Rust:
```rust
impl Session {
    pub async fn reset_app_data(&self) -> Result<u64, ExpectationFailure>;
}
```

TypeScript / Swift / Kotlin equivalents. Same semantic across the four; each drives the runner endpoint.

### D4 — Adaptive app-alive cache re-probe (v1.0.7 §"What's next" carryover)

Insight's item B secondary observation: `pinning-failure.yaml` fails with `unknown` a11y tree, suspected root cause = the v1.0.5 §D2 app-alive cache marking dead for a hard 20 s window while the app is actually finishing bootstrap.

Change:
- On XCTIssue "Application X is not running" observed: mark bundle dead for 20 s (unchanged).
- During the window, a background task on the runner fires a lightweight `snapshot()` probe every 3 s. If the snapshot returns a non-empty tree, invalidate the cache immediately — the app came back before the window closed.
- On invalidation, log `smix-runner: app-alive cache invalidated early for <bundle> (probe hit at <ms>)` to stderr for operator visibility.

Cost: max ~6 extra `snapshot()` calls per dead window. Well under the pacer floor.

### D5 — Supervisor `RunnerCycled` reason with log context

Insight's v1.0.7 shipping doc "What's next" flagged: current `RunnerCycled` JSON events just carry the matched line. Extend to include ±10 lines of surrounding log context:

```json
{
  "event": "RunnerCycled",
  "reasonMatched": "** TEST INTERRUPTED **",
  "context": [
    "2026-07-11 14:32:04 IDETestOperationsObserverDebug 645.912 elapsed",
    "2026-07-11 14:32:04 SchemeActionResultOperation started unexpectedly",
    "** TEST INTERRUPTED **",
    "2026-07-11 14:32:05 xcodebuild[52341] test-host process 3212 exited"
  ],
  "atMs": 1720689124321
}
```

Consumers wire the context into their gate report so cycle-cascade analysis stops requiring a separate `grep` of the runner log.

## Wire additions (additive-only)

- `POST /session/reset-app-data {sessionId}` → 200 `{ok, wallMs}` / 404 `{error: "unknown session id"}`.
- `SessionResetAppDataRequest` / `SessionResetAppDataResponse` in `smix-runner-wire`.
- `Session::reset_app_data()` on all 4 SDKs.
- Yaml verb `clearAppData` in `smix-verbs` + adapter.

## ABI additions (additive-only)

- New enum variant `Step::ClearAppData` in adapter-maestro (parser + runtime).
- `HttpRunnerClient::reset_session_app_data(req)` method.
- `Session::reset_app_data()` method on all 4 SDKs.
- Deprecation `#[deprecated(since = "1.0.8", note = "use Session::reset_app_data")]` on `App::launch_fresh` with `clear_state = true` shape — soft deprecation, no code removal in 1.x.

## Deferred to v1.0.9+

- **Full removal of `simctl uninstall + install` code path.** Kept in v1.0.8 as the last-resort `SMIX_LAUNCH_FRESH_FORCE_REINSTALL=1` opt-in for consumers who need bit-identical reinstall (rare — only meaningful when the app's `.app` bundle itself changed on disk).
- **Removing the `Terminate` op from the `SandboxClearInPlace` path.** Once D1 lands, the in-process `XCUIApplication.terminate() + FileManager wipe + XCUIApplication.launch()` becomes the DEFAULT path. `plan_launch_fresh_calls_v2` continues to emit the `SandboxClearInPlace` sequence for consumers not on the session lifecycle (rare and shrinking); D1 handles the common case.

## Rollout

Standard 4-ecosystem publish. Priority items D1 + D2 + D3 land together (they are one systemic answer to insight's hard requirement). D4 + D5 land in the same version but the D1-D3 batch is the release gate.

**Timeline**: 1-2 days. D1 runner-side is the biggest change; D2 + D3 are additive wire + SDK plumbing on top.
