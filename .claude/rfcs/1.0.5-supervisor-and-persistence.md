# RFC — smix 1.0.5 supervisor + session persistence + real-sim smoke gate

Status: DRAFT — planned charter, no implementation yet
Date: 2026-07-11
Triggers:
- v1.0.4 CHANGELOG "Deferred to v1.0.5" — three named charters
- v1.0.4 shipping caveat "shipped on build-green + unit tests, NOT on real-sim smoke tests" — established v1.0.5 as the release that closes the real-sim verification gap
- Prior: `.claude/rfcs/1.0.4-sim-health-and-backpressure.md`

## Framing

v1.0.4 was the "close the feedback backlog" release (all 9 §A-§I items landed + SimRenderServer stress fix + lifecycle-safe-exit). It shipped with three known gaps:

1. **§E ask 2 — Session persistence across XCTest lifecycle.** When the test-host restarts, the in-memory session table is lost; consumer's `Session-Id` becomes stale → falls through to legacy per-request path.
2. **§D6 — Host-side XCTest supervisor daemon.** v1.0.4 gives consumers the raw material (`Session::state` events + `smix runner cycle` verb) but no automatic cycler.
3. **Runner-side idle-close 120 s → 60 s tightening.** Half-orphaned sessions (SIGKILL wipes client without close) linger up to 2 minutes today.

Plus one operational lesson from the v1.0.4 ship arc:

4. **Real-sim smoke test framework.** v1.0.4 shipped on build-green + unit tests. The Swift-side S5/S6/S14 runtime paths (rate limit / cache TTL / sandbox clear) were compile-verified but never runtime-verified on a real sim before consumers pulled the release. v1.0.5 closes this by making a real-sim smoke a hard release gate.

Every consumer whose current gate loop shipped against v1.0.4 has a workaround already: manual `smix runner cycle` after `TEST INTERRUPTED`, or `Session::state === 'dead'` → bail. v1.0.5 upgrades those from opt-in to automatic — nothing v1.0.5 breaks v1.0.4 consumers.

## Decisions

### D1 — Session persistence across XCTest lifecycle (§E ask 2)

**Problem.** Today the session table lives in `SmixRunnerUITests.swift` process memory:

```swift
sessions.lock()
sessionTable[sid] = entry
sessions.unlock()
```

When xcodebuild restarts the test-host process (either after `** TEST INTERRUPTED **` or after a client-invoked `smix runner cycle`), `sessionTable` is empty on the next boot. Every open session id known to consumers is now unknown to the runner — subsequent requests fall through to the legacy per-request rebind path.

**v1.0.5 solution.** Persist the session table to a small on-disk file, load at test-host boot, atomic writes on every mutation. File lives under the runner root: `.smix/runner/sessions-<UDID>.json`. Schema:

```json
{
  "schema": 1,
  "sessions": [
    {
      "sessionId": "9F3E8B1A-...",
      "bundleId": "com.example.app",
      "openedAtMs": 1720689000000,
      "activatedOnceOnOpen": true,
      "lastActivatedAtMs": 1720689042000
    }
  ]
}
```

Behavior:
- **Boot**: read file if present; rebuild `sessionTable` with fresh `XCUIApplication` bindings for each session id + bundle-id pair (no `.activate()` — the client will send its next request soon and we rebind then).
- **Mutation (open / close / relaunch / closeAll)**: atomic-rename write. Cheap because ≤10 sessions typical.
- **Corruption / schema mismatch**: log + start empty (safe).
- **Runner cycle invariant**: `smix runner cycle` preserves the session file (only `derived-data-<UDID>/` and the xcodebuild process are cycled). Consumer's `Session-Id` remains valid through the cycle.

**Wire additive**: `POST /session/list` → `{sessions: [{sessionId, bundleId, openedAtMs, lastActivatedAtMs}]}`. Useful for diagnostics + the supervisor (below); consumers can call it to enumerate what they might still have open.

**SDK surface additive**: `Session::still_valid()` probes `/session/list` and returns `true` iff the session id is known to the runner. Consumers wire this after a `Session::state === 'cycling'` transition to decide whether to keep using the session or reopen.

### D2 — Host-side XCTest supervisor daemon (§D6)

**Problem.** v1.0.4 detects `TEST INTERRUPTED` via the runner-side log at `~/workspace/*/.smix/runner/runner-<UDID>.log`, but no v1.0.4 code automatically cycles. The manual escape hatch is `smix runner cycle`.

**v1.0.5 solution.** A supervisor daemon that watches the runner log for the interrupt patterns + runs `smix runner cycle` automatically.

**Shape**: standalone command `smix runner supervise [--udid <udid>] [--patterns ...]`.

- Starts in the foreground, prints a heartbeat every 30 s.
- Tails `.smix/runner/runner-<udid>.log`; matches against a small set of interrupt patterns:
  - `** TEST INTERRUPTED **`
  - `SchemeActionResultOperation started unexpectedly`
  - `IDETestOperationsObserverDebug` followed by an elapsed line that doesn't converge
- On match: invokes `smix runner cycle` internally (reuses the same code path as the CLI verb — not a separate subprocess). Logs a `RunnerCycled { reason, at_ms }` structured event to stdout that CI can grep.
- Backoff: max one cycle per 60 s (a spurious detection during boot is common). If interrupts persist for > 5 cycles in 10 minutes, exits non-zero so a monitoring layer can escalate.
- Session persistence (D1) means cycled sessions survive — consumer's flow resumes without reopening.

**Deployment shapes** — user picks:

1. **Sidecar via `smix runner up --supervise`** — the CLI spawns the supervisor as a detached child process on `up`. Best for laptops (simple).
2. **Standalone `smix runner supervise`** — user runs it in a separate terminal / `pm2` / `systemd`. Best for shared CI.
3. **Managed by another tool** — user forwards `smix runner supervise` under whatever they already use (docker, launchd).

pid-registry (per project convention) records the supervisor's PID so subsequent `smix runner down` can also tear it down.

### D3 — Runner idle-close 120 s → 60 s tightening

Small change on the runner side: reduce the idle-sweep interval + the per-session idle threshold. Session that hasn't been touched in 60 s → auto-`close`. Client that pings `/health` counts as touching all its open sessions (already the case). SIGKILL-orphaned sessions vanish within 1 minute instead of 2.

Also: emit a debug log line on idle-close so operators can see it happening.

### D4 — Real-sim smoke gate

**Problem.** v1.0.4 shipped on build-green + unit tests. The Swift-runtime paths for `PopupPacer`, `AppAliveCache`, `SessionRelaunchApp`, and `SandboxClearInPlace` were compile-verified but never runtime-verified. This is fragile — a bug in any of them would land in front of consumers who then pay the yank + emergency-v1.0.5 cost.

**v1.0.5 solution.** A smoke gate script `scripts/release/smoke-v1.smoke.sh` that runs a fresh sim boot + a small yaml flow exercising every net-new v1.0.4/v1.0.5 code path, and MUST pass green before publish. Gate lives under `scripts/release/` for discoverability.

Contents (fixture yaml + shell driver):

- Boot sim-smoke (dedicated sim UDID reserved for release smoke).
- `smix runner up sim-smoke --bundle com.example.smoke-target` (verifies §D8 bundle validation).
- `smix run smoke.yaml --activate --bundle-id com.example.smoke-target --debug-output /tmp/smoke-out`.
  - yaml exercises: `takeScreenshot` × 20 in quick succession (verifies pacer floor kicks in + no SimRenderServer crash), `assertVisible` failing on a nonexistent id (verifies fail.tree.json emit), `launchApp: clearState: true` (verifies §D12 in-place clear), a Session-scoped `relaunch_app` inline.
  - Verify: `/tmp/smoke-out/run-summary.json` has non-empty `steps: [...]` with expected `wallMs`, tree_path on the failure, pacer's `429` seen in runner log (grep).
- `smix runner cycle` (verifies §D5 wire endpoint + session persistence).
- Second `smix run` reusing the same session id (verifies D1 persistence — the second flow's first request should NOT return `unknown session id` because the sessions file was reloaded on cycle).
- `smix runner supervise` for 30 s alongside a synthetic `TEST INTERRUPTED` injected into the log (verifies §D2 detection).
- `smix runner down`.

Exit 0 = green; nonzero = block publish. Runs as part of the DAG-ordered ship script.

**Ship gate**: `scripts/release/ship.sh 1.0.5` refuses to run if the smoke gate hasn't passed in the last hour. Manual bypass via `--i-know-what-im-doing` (matched in the code to only work on release-candidate branches).

## Wire + ABI additions (additive-only)

- `POST /session/list` — new route; response `{sessions: [{sessionId, bundleId, openedAtMs, lastActivatedAtMs}]}`.
- `HttpRunnerClient::list_sessions(&self) -> Result<SessionListResponse>` on Rust client + parallel on TS/Swift/Kotlin runtimes.
- `Session::still_valid()` on all 4 SDKs.
- `smix runner supervise` + `smix runner up --supervise` CLI.
- `smix runner list-sessions` CLI verb for interactive diagnostics.

## Non-goals for v1.0.5

- ~~Full XCUITest restart-in-place~~. The persistence file makes the cycle transparent; restarting XCUITest without a full xcodebuild spawn is v1.1 material.
- ~~Multi-sim supervisor federation~~. One supervisor per runner is the v1.0.5 shape; a cross-sim orchestrator is out of scope.
- ~~Non-`sim-smoke` real-sim regression~~ (i.e. a full-corpus stress). The smoke gate is a smoke, not a stress; a stress harness is v1.1 material.

## Rollout plan

Standard 4-ecosystem publish:

1. `scripts/release/smoke-v1.smoke.sh` — must exit 0.
2. `cargo release` DAG order (same as v1.0.4 sequence).
3. `npm publish` + `gradle publish` + `swift-v1.0.5` tag.
4. Update `docs/ai-guide/insight-v1.0.5-shipping.md` + share fullpath to insight.

**Timeline estimate**: 1-2 weeks from v1.0.4 ship. D1 + D3 are 1-2 days each; D2 is a solid week (state machine + subprocess mgmt + testing). D4 smoke gate 2-3 days.

**Cadence**: no v1.0.5-rc phase — the smoke gate replaces the RC role. Ship v1.0.5 direct once smoke green + code-review pass.
