## Ground-truth forensic on the "hub-form.png" anomaly

Running pixel + chunk comparison on the actual baseline vs current PNG:

| | Baseline 2026-07-08 17:46 | Current 2026-07-09 02:51 |
|---|---|---|
| Dimensions | 1206 × 2622 RGBA | same |
| Chunks | `IHDR + sRGB + eXIf + 10×IDAT + IEND` | `IHDR + 1×IDAT + IEND` |
| Size | 158 104 bytes | 91 404 bytes |
| Colorspace | `sRGB IEC61966-2.1` (ICC) | none |
| IEND validity | ok, 0 trailing bytes | ok, 0 trailing bytes |
| Decoded RGBA sha256 | `93301ba8cb5d9c4c…` | `41b1d05ca508352b…` |
| **Pixel diff** | — | **27.67 % of pixels differ, max channel Δ = 255** |

The 27.67 % pixel diff with max channel Δ = 255 rules out "encode metadata drift" as the primary cause. The two PNGs capture materially different screen states — the current run genuinely captured a mid-transition frame with a red block covering the form's upper half. The missing `sRGB` / `eXIf` chunks are an independent secondary effect (iOS 26.5 `simctl io screenshot` sub-build variability); they only affect downstream viewers that fall back to Display P3 when no ICC is embedded, they do NOT affect dhash / hamming pixel-comparison.

Trace of the capture pipeline confirms zero smix re-encoding:
`App::screenshot()` → `IosDeviceControl::screenshot(udid)` → `SimctlClient::screenshot(udid)` → `xcrun simctl io <udid> screenshot <tmpfile>` → `std::fs::read(tmpfile)` → return bytes. Every byte is passthrough from `simctl io`. The 27.67 % pixel diff is what `simctl` observed on the sim screen.

**Conclusion**: what looked like "two independent bugs" (activation crash + rendered PNG走样) collapses to **one root cause with two clinical presentations along a severity axis**:

- **Presentation A** (long sessions, > ~340 s): `resolveApp()` per-request `.activate()` accumulates ~1130 calls, XCTest process arbitration exhausts, `test_runForever()` crashes → all downstream requests return stale/empty → visual gate reports 10-19 % diff + `metric=-1`
- **Presentation B** (medium sessions, before the crash boundary): app is repeatedly re-activated but runner is still alive → `simctl io screenshot` catches the app mid-transition (pull-to-refresh stuck expanded, SpringBoard event overlay bleeding through, a11y highlight residue) → captured pixels genuinely show the mid-state red block + yellow-outlined text seen in `hub-form.png`

Bug B was never a smix encoder bug — it was smix's activation storm making the app snapshot un-clean before `simctl io` fired.

## Independent secondary observation

iOS 26.5 sub-build (between 2026-07-08 morning and 2026-07-09) changed `simctl io screenshot` to omit the `sRGB` and `eXIf` chunks. This is an Apple-side change, not a smix regression. Effects:

- **Zero effect on pixel-comparison** (dhash decodes IDAT to RGBA array; ancillary chunks are ignored)
- **Cosmetic effect on Preview.app**: viewers without an embedded ICC profile fall back to Display P3 on wide-gamut Macs, over-saturating red and adding yellow anti-alias fringing to text — this is what visually made `hub-form.png` look "corrupted" when opened in Preview

This is treated as a downstream-convenience issue, addressed by (2) below without touching pixel bytes.

## The two clinical presentations (original section, kept for reference)

**Bug A — activation storm → runner crash → silent downstream corruption**

- `SmixRunnerUITests.swift:760-777` `resolveApp()` unconditionally calls `XCUIApplication.activate()` whenever `RequestContext.activate == true` (which is per-request when client sends `--activate`)
- Long sessions (insight's visual+perf gates ≈ 340 s) accumulate ~1130 activation calls at ~300 ms cadence, exhausting XCTest process arbitration on iOS 26.5
- `test_runForever()` crashes, XCTest restarts with an empty selector → **`TEST FAILED`** but the runner process technically stays up
- Downstream requests silently return corrupted / stale data:
  - `/tree` → `snapshot_unavailable` handled as retry
  - `/screenshot` → mid-restart transient state captured
  - `smix run` exit code falls through as `metric=-1`
- Consumer only realises the runner died by observing "screenshots don't match baseline + perf metrics missing" (10-19 % visual diff, `metric=-1`, no product-side UI change)

**Bug B — screenshot rendering走样**

- The `hub-form.png` etc. show:
  - Top ~40 % of screen rendered as a solid red block covering the form's upper half
  - Multiple layers of "Refreshing…" text with yellow-outlined stroke visible in the red block
  - Yellow stroke effect on element labels ("Form components", "FormInput — filled", "jane.doe@example.com")
  - Below the red block, form content is present but visibly faded / dimmed
- This shape is inconsistent with a plain `simctl io screenshot` of an idle app screen. Candidates:
  1. iOS 26.5 XCTest debug-overlay is active during `test_runForever`, `simctl io screenshot` captures the composite of app + overlay
  2. `SmixA11ySwizzle` `snapshotParameters` swizzle (mode=modal-honor=off) interacts with iOS 26.5's a11y-highlight renderer, producing yellow-outlined text
  3. Pull-to-refresh state stuck expanded because the app never got main-thread time during the activation storm — captured screenshots caught the app mid-transition
  4. Colorspace metadata bug in the PNG chain

The bugs are **not independent** — they share a root cause: **smix has no typed contract at the runner boundary**. Client fires requests, runner processes each in isolation with no session model, screenshots flow back with no integrity metadata, and failures manifest as silently-corrupted downstream artifacts rather than explicit typed errors.

## Systemic gap

The single missing capability, stated positively:

> Smix's runner boundary is a wire protocol with an **implicit** contract. Each request is stateless from the runner's POV; downstream artifacts (screenshots, a11y snapshots, exit codes) carry **no metadata** describing capture context; the client has **no observability** into whether the runner is alive, degraded, or drifted since the last request.

Both bug A and bug B fit inside "corrupted output because nothing in the pipeline enforces a contract".

The systemic fix is not "cache activation" and "verify PNG magic". Those are point patches. The systemic fix is: **make the runner boundary a first-class stateful contract with explicit session lifecycle, capture-metadata annotations on every artifact, and client-side liveness observability**.

## Pixel-preservation invariant (added after user directive 2026-07-09)

> Screenshots are the source of truth for pixel-comparison / visual regression.
> Any byte emitted by `simctl io screenshot` (or the equivalent runner-side
> capture) reaches disk unchanged unless the caller **explicitly** requested
> a mutation (yaml `takeScreenshot: { annotate: [...] }` or CLI
> `--debug-output` fail-annotate path).

Implications for the fix:

- **NO decode → re-encode** of PNG bytes in any auto path
- **sRGB chunk normalization** (fix #2 below) MUST operate on the raw byte stream — insert the 13-byte `sRGB` chunk before the first IDAT without touching IDAT bytes; the chunk carries only a 1-byte rendering-intent value (0 = perceptual), no color data
- **Companion metadata** (fix #4 below) goes into a sidecar `.meta.json`, not into the PNG's ancillary chunks

## Proposed capability — v1.0.2 scope

Four orthogonal but coordinated additions.

### 1. Session lifecycle (fixes root cause of BOTH presentations)

**Contract**: A `Session` is bound to `(bundle-id, activation-mode)` from the moment it's opened until it's explicitly closed or the runner detects app drift.

New wire:

- `POST /session/open  { bundleId, activate?: bool }` → 200 `{ sessionId, activatedOnce: bool }`
  - Runner allocates a `SessionId` (uuid), stores `(sessionId → XCUIApplication binding)` in a session table
  - If `activate=true` on open, activates once on-main and records `activatedAtMs`
- Every subsequent request accepts `Session-Id: <id>` header
- Handler reads the session from the table; NO per-request `.activate()` regardless of `App-Activate` header value
- `POST /session/renew-activation { sessionId }` → 200 — explicit escape hatch when the client detects app drift (e.g. `/tree` returned `snapshot_unavailable`); rate-limited to at most once per 2 s per session
- `POST /session/close { sessionId }` → 200

Backward compat: absent `Session-Id` header falls through to the legacy per-request `resolveApp()` path but with rate-limited activation (max 1 activate per bundle-id per 5 s).

**Consumer migration** (opt-in, no forced change):

```typescript
const s = await smix.openSession({ bundleId: 'com.example.app', activate: true })
try {
  await s.tap({ id: 'btn-login' })
  await s.fill({ id: 'email' }, 'user@example.com')
  const png = await s.screenshot()
} finally {
  await s.close()
}
```

Insight's stage code becomes: open session at gate start → run all steps → close. `bun verify visual`'s 340 s session issues ONE `activate` instead of ~1130.

### 2. sRGB chunk normalization (raw-byte splice, pixel-safe)

**Contract**: If `simctl io screenshot` (or the equivalent runner-side capture) emits a PNG without an `sRGB` ancillary chunk, smix inserts one before the first IDAT — WITHOUT decoding, re-encoding, or touching any pixel byte.

Rationale: this is a downstream-convenience fix (macOS Preview.app / dev-tool PNG viewers gracefully render the sRGB color they should); it does NOT affect pixel-comparison correctness (dhash / hamming ignore ancillary chunks); it preserves the pixel-preservation invariant above.

Implementation site: `smix-simctl::SimctlClient::screenshot()` post-capture, at the byte-slice level:

```rust
// After the tmp file is read into `bytes`, before returning:
let bytes = normalize_png_srgb_chunk(bytes);
```

Where `normalize_png_srgb_chunk`:

1. Verifies PNG magic (8 bytes)
2. Walks chunks; if `sRGB` seen before `IDAT` → return input unchanged
3. If first `IDAT` reached without seeing `sRGB` → splice a 13-byte `sRGB` chunk (length=1, type="sRGB", data=[0], crc=<computed>) into the byte stream at the position of first IDAT
4. Return the spliced bytes

Total operation: no PNG decode, no image crate involvement, ~30 LOC pure byte-slice math. `crc32fast` (already in deps via oxipng) computes the chunk CRC.

Consumer effect: the 91 KB PNG becomes 91 417 bytes (+13). Pixel data unchanged (verified by `Image.open(...).convert('RGBA').tobytes()` sha256 match). Preview.app color renders correctly. dhash regression tests unaffected.

### 3. Runner liveness observability (fixes presentation A downstream corruption)

**Contract**: Client-side detects runner-side degradation early and surfaces as a distinct error class, not silent corruption.

Client changes (`smix-runner-client`):

- Track a rolling window of last N (=8) request outcomes (success / snapshot-unavailable / connection-refused / 5xx)
- If ≥ 3 of last 4 are non-success → surface `RunnerDegraded { last_meta, window }` on subsequent calls
- On connection-refused specifically: try `/health` once with 1 s timeout; if unreachable → `RunnerDied { last_seen_ms, last_error }`
- These are new variants on `RunnerTransportError`; existing error handling paths get a new arm

Runner changes (Swift):

- `/health` endpoint now returns `{ ok: true, uptimeMs, lastRequestAtMs, sessionsOpen: N, activationsTotal: M }`
- Consumer or client-side logic can detect "runner is silent for > 30 s" as a soft failure

### 4. Capture companion `.meta.json` (forensic trail)

**Contract**: Every PNG written to disk by a smix code path (yaml `takeScreenshot: { name: "…" }`, CLI `smix screenshot`, `--debug-output` fail-PNGs) is accompanied by a sidecar `<name>.meta.json` with capture provenance.

Fields:

```json
{
  "smixVersion": "1.0.2",
  "runnerVersion": "1.0.2",
  "capturedAtMs": 1720489907843,
  "sessionId": "…" | null,
  "sessionUptimeMs": 12345 | null,
  "activationsInSession": 1,
  "captureBackend": "simctl-io-screenshot" | "xcuiscreen-main-screenshot",
  "iosVersion": "26.5.1" | null,
  "xcodeVersion": "16.3" | null,
  "udid": "…",
  "pngSizeBytes": 91417,
  "pngSha256Hex": "…",
  "pixelWidth": 1206,
  "pixelHeight": 2622,
  "srgbChunkPresent": true,
  "srgbChunkSource": "simctl" | "smix-normalized",
  "chunks": ["IHDR", "sRGB", "IDAT", "IEND"]
}
```

The PNG itself stays byte-identical to what `simctl io` produced (plus the optional sRGB splice from fix #2). The `.meta.json` is the audit trail.

For pixel-comparison consumers: ignore the sidecar. For forensic / gate-debugging: the sidecar has everything to bisect an anomaly (was it a specific iOS build? was the session too old? did activation count balloon?).

For insight's `bun verify visual`: their `collectScreenshots(outDir)` can start indexing the sidecars alongside the PNGs, cross-check `sessionUptimeMs` on failing anchors ("this diff correlates with sessionUptimeMs > 300 s"), and pin baselines to a known sessionUptimeMs distribution.

## Non-goals for 1.0.2

- **Rate limiting** on the client side (token bucket etc.) — belongs in 1.1
- **Retry-with-recovery** heuristics (auto-restart runner on death) — belongs in a separate reliability layer
- **Fixing bug B's iOS 26.5-specific rendering** if it turns out to be caused by iOS `SmixA11ySwizzle` interaction — that's investigative work per capture metadata; if diagnosed, the fix may be to disable the swizzle by default and gate behind `SMIX_A11Y_MODAL_HONOR=off` opt-in

## Wire compatibility

- **Session routes** are all-new — no existing route changes shape
- **Legacy path** (no `Session-Id` header) works byte-identical, only diff = activation rate-limited to 1/5s instead of every-request
- **Metadata header** on screenshot response is additive — client that doesn't parse `X-Smix-Capture-Meta` still gets the same `{ png_base64 }` body
- All of the above keeps v1.0.x wire-additive; v1.0.2 remains semver-compatible with v1.0.1 clients

## ABI compatibility

- New enum variants on `RunnerTransportError` (`RunnerDegraded`, `RunnerDied`) — `#[non_exhaustive]` already in place, so this is compatible
- No signature changes on stone crates
- Session type + SDK builder additions on `smix-sdk` — new `App::open_session`, `App::from_session`; existing `App::connect_to_runner` unchanged

## Decisions locked (per project principles — user delegated)

Applied §13 (quality/perf >> R&D cost), §12.1 (three-layer sense/decide/act), dogfood iron rule (systemic upgrade not point patch), decomposition-before-polish (real forensic before proposing fix):

- **D1. Session model = default in 1.0.2**, not opt-in. `smix run` opens a session at CLI entry, closes on exit; all SDKs (Rust / TS / Swift / Kotlin) use session-backed clients as the default constructor. Rationale: opt-in leaves the storm bug latent on wire for every `--activate` consumer. Legacy raw-HTTP path (no `Session-Id` header) is preserved wire-compat with a rate-limited fallback so v1.0.1 clients keep working, but they get the rate-limit benefit for free.
- **D2. Bug B is not a separate bug**. Pixel forensic (27.67 % diff, max Δ 255) confirms it is presentation B of the activation storm. Session lifecycle (D1) fixes it directly. No delegation of root-cause investigation to the consumer; no capture-metadata-as-a-fix pattern.
- **D3. sRGB chunk normalization at the byte level** — no decode, no re-encode, pixel bytes untouched. Preserves the pixel-preservation invariant.
- **D4. Rate limit on legacy path = 5 s per bundle-id**. Acceptable for the recovery use case (Preferences / OS preview steals focus, worst-case 5 s of extra drift before re-activate). Longer risks trapping users in stale foreground; shorter risks re-storming.
- **D5. All four SDKs get session parity in 1.0.2**. §12.1 three-layer + capability-must-be-core-flat: dropping Kotlin would break the platform-parity invariant. Kotlin session support ships alongside Rust / TS / Swift.
