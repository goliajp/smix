# RFC — smix 1.0.7 observability layer + subprocess integrity

Status: DRAFT
Date: 2026-07-11
Triggers:
- insight's 2026-07-11 v1.0.5 followup feedback — 3 findings that share ONE root cause
- User directive (2026-07-11): "反馈得到的是点，我们要变成体系" — feedback surfaces points, we ship systems

## Framing — one root cause behind three feedback points

Insight's v1.0.5 followup reports three "distinct" problems:

- **Item A** — cold recompile after version bump takes > 5 min, `spawnSync` timeout=300 s fires prematurely. Consumer thinks smix failed. Consumer bumps to 600 s.
- **Item B** — mid-flow error `xcrun simctl spawn exited 2: No such file or directory`. Consumer has no way to know WHICH `simctl spawn` fired, WHICH argv failed, WHICH binary was missing.
- **Item D.3** — supervisor's `{"event":"RunnerCycled",...}` JSON may have been buffered when insight tore down mid-flow; events lost.

Each looks like its own bug. They share a systemic gap: **smix is opaque about its own runtime**.

- A: no progress signal during long operations → consumer can't distinguish "still working" from "stuck".
- B: subprocess errors don't carry argv → consumer can't reproduce, can't self-fix, can't file precise repro.
- D.3: streaming events are buffered → consumer doesn't see cycle activity that IS happening.

Fixing each in isolation is a point patch. The systemic move is a **runtime observability layer** that makes every subprocess invocation, every long-running operation, and every progress event first-class inspectable — for insight today and every future consumer forever.

## Ground-truth on the specific `simctl spawn exited 2` in item B

Before designing the observability system, resolve the immediate ground-truth: **which** `simctl spawn` fires with ENOENT in insight's flow?

Grep `smix-simctl` for `simctl_run(&["spawn"`:

- `SimctlClient::clear_app_sandbox` (v1.0.4 §D12, `.claude/rfcs/1.0.4-sim-health-and-backpressure.md`) invokes:
  ```rust
  simctl_run(&["spawn", udid, "rm", "-rf", &documents, &library, &tmp]).await?;
  ```
  Notice: `"rm"` is not an absolute path. `xcrun simctl spawn <UDID> <cmd>` uses `posix_spawn` inside the sim OS — on iOS 17+ the `<cmd>` must be an absolute path (`$PATH` resolution is not run). Real bug on the v1.0.4 code path insight triggers when their `launchApp: clearState: true` yaml verb fires — which happens in every bootstrap flow.

  Consequence: v1.0.4 §D12 in-place clear implementation is broken on iOS 17+ simulators. The fix is trivial (`"/bin/rm"`), but insight had no way to diagnose it because the error message from smix says `spawn exited 2: NSPOSIXErrorDomain code 2` without the argv `["rm", "-rf", <container>/Documents, ...]` that would have made the missing absolute path obvious.

- Other `simctl_run(&["spawn"` sites: `defaults read` / `defaults write` for locale enforcement (`current_locale` / `set_locale`) — those use `defaults` which is at `/usr/bin/defaults` inside the sim. Might be OK because `/usr/bin` is in the sim's default PATH, but let's normalize all of them.

So item B has **both** a direct fix AND a systemic gap. v1.0.7 does both.

## Decisions

### D1 — Absolute paths for every `simctl spawn` inside smix

Direct fix for item B root cause. Every `simctl_run(&["spawn", udid, <cmd>, ...])` in smix-simctl uses an absolute path:

- `"rm"` → `"/bin/rm"` in `clear_app_sandbox`.
- `"defaults"` → `"/usr/bin/defaults"` in `current_locale` and `set_locale`.
- Any future `simctl spawn` addition must go through an internal helper that asserts the command starts with `/`.

Cost: trivial. Preserves current behaviour on any simulator where PATH happened to be right, fixes the failing case explicitly.

### D2 — `SubprocessError` with argv + captured stderr + duration

The systemic fix at the SDK boundary. Currently `SimctlError::NonZeroExit { subcommand, code, stderr }` records ONLY the subcommand name (e.g., `"spawn"`) — never the full argv. Change to:

```rust
pub enum SimctlError {
    ...
    NonZeroExit {
        subcommand: String,
        argv: Vec<String>,              // NEW — full argv passed to xcrun simctl
        code: i32,
        stderr: String,
        wall_ms: u64,                    // NEW — how long the invocation ran
    },
    ...
}
```

The `Display` impl surfaces argv in the message:

```
xcrun simctl spawn <UDID> rm -rf /Users/.../Documents /Users/.../Library /Users/.../tmp exited 2 (312ms): The operation couldn't be completed. No such file or directory
```

Now insight (or any consumer) reads the error and knows immediately WHAT smix asked simctl to do and WHY it failed. This alone would have let insight self-diagnose D1.

Additive: `#[non_exhaustive]` on `SimctlError` means adding fields is not a breaking change if we push it to a minor release. But since v1.0's stability guarantee for stone crates is additive only WITHIN a minor, we can either:
- Add new variant `NonZeroExitWithArgv { ... }` and keep old `NonZeroExit` as-is (backward compat), OR
- Add `argv` + `wall_ms` fields with `#[serde(default)]` semantics (the enum is not serialized, so the compat concern is only match sites).

Chosen: extend the fields directly. The workspace grep found only 8 match sites for `SimctlError::NonZeroExit`; none of them destructure new fields, so extension is safe.

### D3 — Ring buffer of recent subprocess invocations

Every `simctl_run` invocation records to a global (per-`SimctlClient`) ring buffer:

```rust
pub struct SubprocessRecord {
    pub argv: Vec<String>,
    pub exit_code: Option<i32>,           // None on spawn error
    pub wall_ms: u64,
    pub stderr_head: String,               // first 256 bytes
    pub timestamp: SystemTime,
}
```

Buffer size 128 by default; configurable via `SimctlClient::with_subprocess_ring_size(usize)`. Accessible via `SimctlClient::recent_subprocesses(&self) -> Vec<SubprocessRecord>`.

Purpose: when a consumer or supervisor sees an error, they can dump the ring buffer for post-mortem. Not exposed on the wire yet in v1.0.7 (that's D5); the buffer is process-local and the CLI accesses it via `smix diagnostic dump`.

### D4 — `smix diagnostic dump` CLI verb

New verb. Prints the ring buffer of the currently-running smix CLI process — but more usefully, sends `POST /diagnostic/dump` to the runner and prints ITS ring buffer.

```bash
$ smix diagnostic dump
=== runner-side subprocesses (last 20 of 128) ===
2026-07-11 15:34:12.412  simctl spawn <UDID> rm -rf ...        code=2   312ms  err=No such file or directory
2026-07-11 15:34:11.998  simctl get_app_container <UDID>       code=0   410ms
2026-07-11 15:34:11.412  simctl terminate <UDID> ...            code=0   201ms
...
=== client-side subprocesses (last 20 of 128) ===
(empty — no simctl calls from this smix CLI invocation)
```

The runner-side ring buffer requires D5.

### D5 — Runner-side `POST /diagnostic/dump` route

Runner exposes a new route returning the runner's own subprocess ring buffer + a snapshot of the session table + supervisor pid + sim health state. Response shape:

```json
{
  "recentSubprocesses": [{
    "argv": ["simctl", "spawn", "<UDID>", "/bin/rm", "-rf", "..."],
    "exitCode": 2,
    "wallMs": 312,
    "stderrHead": "The operation couldn't be completed. No such file or directory",
    "timestampMs": 1720689252412
  }],
  "sessions": [ ... ],
  "simHealth": "healthy",
  "supervisorPid": 91234
}
```

Additive-only route. v1.0.6 clients get 404 → CLI prints "runner too old for /diagnostic/dump; upgrade to v1.0.7+" and dumps only the client-side buffer.

### D6 — Streaming discipline for long-running processes

Every long-running smix process (`runner supervise`, `runner up` progress banners, `run` per-step logs) sets stdout to line-buffered explicitly:

```rust
use std::io::Write;
let mut out = std::io::stdout().lock();
writeln!(out, r#"{{"event":"RunnerCycled","at":{now}}}"#)?;
out.flush()?;
```

Fixes item D.3 — supervisor JSON events reach the consumer's parser even when the flow errors mid-cycle.

Additionally: `smix runner supervise --json` flag switches ALL output to structured JSON lines instead of the current mixed human + JSON. Consumer parsers can rely on every line being valid JSON.

### D7 — Cold-rebuild progress banner

Fixes item A. Before invoking `xcodebuild`, `smix runner up` checks whether `.smix/runner/derived-data-<UDID>/` exists + is populated:

- Warm path (derived-data present + fresh): print `runner up: warm rebuild expected ~3 s`.
- Cold path (derived-data missing OR stale after version bump): print `runner up: COLD REBUILD expected up to 10 minutes (recompiling XCUITest bundle for smix <version>)`, then emit a heartbeat every 30 s with `runner up: xcodebuild still working ({elapsed}s elapsed)`.

Consumers with a `spawnSync` timeout know how much to budget. No timeout expected because insight already bumped to 600 s.

### D8 — App-alive cache re-probe during window

Insight's item B secondary observation: `pinning-failure.yaml` fails with unknown a11y tree, which points to the v1.0.5 D2 app-alive cache having marked the app dead after XCTIssue and blocking `/tree` for 20 s while the app was actually finishing bootstrap.

Change the cache from "hard 20 s dead" to "probe every 3 s during the window":

- On first `Application not running` XCTIssue: mark dead for 20 s.
- Every 3 s during the window, background probe: fire a `/tree` request WITH cache bypass. If it returns a non-empty tree, invalidate the cache immediately.

Cost: one extra `/tree` invocation every 3 s during a dead window (max 6 during 20 s). Cheap. Consumer sees the app come back the moment it's actually alive.

## Wire additions (additive-only)

- `POST /diagnostic/dump` — new route. `SessionListResponse` shape roughly `{recentSubprocesses, sessions, simHealth, supervisorPid}`.
- `HttpRunnerClient::diagnostic_dump()` — Rust client method.
- CLI: `smix diagnostic dump` verb.
- CLI: `smix runner supervise --json` flag (default false; behaviour unchanged when omitted).

## ABI additions (additive-only)

- `SimctlError::NonZeroExit` gains `argv: Vec<String>` + `wall_ms: u64` fields. Legacy match sites that use `..` skip pattern continue to work.
- `SimctlClient::recent_subprocesses(&self) -> Vec<SubprocessRecord>` new accessor.
- `SubprocessRecord` new public struct.

## Non-goals

- Full OpenTelemetry / structured tracing — that's v1.1+ material. v1.0.7 is a targeted observability layer at the specific pain points, not a general tracing platform.
- Consumer-side "smix debug" plugin. If the observability shape ends up needing extension, v1.1's `smix authoring` charter can bake it in.
- Changing `simctl spawn` invocations to use direct `subprocess` calls instead. simctl spawn semantics + argv passthrough are what we want; the change is in how we CONSTRUCT the argv (D1) and how we HANDLE errors (D2, D3).

## Rollout

Standard 4-ecosystem publish. Priority items D1 + D2 + D6 + D7 land first (they close item B specifically); D3, D4, D5, D8 land in the same version as the systemic-observability set.

**Timeline estimate**: 1-2 days. D1 is 10 lines. D2 is a shape change with mechanical grep-and-replace at match sites. D3 is a `VecDeque` + push/lock. D4 + D5 are the diagnostic route + CLI printer. D6 + D7 are localized behaviour changes. D8 is a background task loop.
