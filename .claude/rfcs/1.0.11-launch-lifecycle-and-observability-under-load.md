Three things still failing under real load:

- **§A1 — `clearAppData` still writes ReportCrash `.ips`.** 3 fresh `Insight-*.ips` files with `bug_type: 309` (`com.apple.launchd.exec_terminated_before_ready`) during a single 45-minute batch. - **§A2 — `aliveCache: null` in `/diagnostic/dump`.** Insight cannot distinguish "re-probe never fired" from "counter code isn't exposed". Plus a fourth thing — **§B — Expo SDK 57 dev-client picker** — the compound. `clearAppData` wipes the dev-client's persisted metro URL. Next launch shows the dev-launcher server picker. In SDK 56 the `exp+focus-ai-app://expo-development-client/?url=...` URL scheme auto-navigated the picker. In SDK 57 it doesn't. Insight's yaml sends the URL, picker stays, `dev-bubble` never appears — every batch fails at the picker.

Insight's business flow is blocked on §B. Every v1.0.10 win they named remains a paper win until §B clears.

### D1 — Direct-capture `appAliveCache` in the diagnostic handler (fix §A2)

Root cause: `SessionHandlers.diagnostic` closure reads
`SmixRunnerServer.currentAppAliveCache` (task-local). If FlyingFox
spawns per-request handlers as unstructured `Task { }` off an internal
actor context, task-local propagation may drop. Insight sees
`aliveCache: null` in the CLI-merged dump payload — jq's rendering of a
missing field.

Fix: capture the `appAliveCache` reference directly in the closure at
`test_runForever()` construction time — same way `sessionTable` +
`bootAt` are captured. Remove the `currentAppAliveCache` task-local
read from the diagnostic path (keep it for the other read sites that
do work — those all fire from the correct task context).

Also gain observability: emit `aliveCache` as an ALWAYS-present object
carrying:

- `wired: bool` — `true` when runner was booted with `appAliveCache`
  non-nil; `false` sentinel makes consumers' "is this feature present"
  probe unambiguous.
- All 8 counter fields, zero-valued when unwired.

Wire compat: additive, `#[non_exhaustive]` + `#[serde(default)]` keep
existing consumers happy.

### D2 — `launchApp` learns `launchArguments` and `launchEnvironment` (fix §B → unblocks §A3)

Extend the `AppLifecycleRequest` wire shape:

```rust
pub struct AppLifecycleRequest {
    pub session_id: String,
    #[serde(default)]
    pub args: Vec<String>,
    #[serde(default)]
    pub env: std::collections::BTreeMap<String, String>,
    #[serde(default)]
    pub wait_for_foreground_ms: Option<u64>,
}
```

Swift-side, the launchApp handler:

```swift
launchApp: { req in
  ...
  await SmixRunnerServer.onMain {
    entry.app.launchArguments = req.args        // was: unset
    entry.app.launchEnvironment = req.env       // was: unset
    entry.app.launch()
  }
  ...
}
```

Consumer yaml:

```yaml
- launchApp:
    args:
      - "-EXInternalMetroPort"
      - "8081"
    env:
      EX_DEV_CLIENT_METRO_URL: "http://localhost:8081"
```

Insight's `.devtools/qa/sim/subflows/launch-fresh.yaml` gets the args
they need to bypass the dev-launcher picker without touching their app
source. The exact arg-name / env-var-name is on insight to determine
(SDK 57 dev-client docs); smix provides the mechanism.

### D3 — Wait for `runningForeground` after launch (fix §A1 bug_type 309)

`bug_type 309 exec_terminated_before_ready` fires when a process exits
before launchd's ready signal. Root-cause chain we suspect:

1. `clearAppData` → `terminateApp` (v1.0.8 §D1 cooperative pathway) succeeds
2. Host-side simctl sandbox wipe succeeds
3. `launchApp` calls `XCUIApplication.launch()` — non-blocking; XCUIApplication returns as soon as launch is DISPATCHED, not when app is READY
4. Consumer's next yaml step (or a batch retry firing another clearAppData) hits `terminateApp` while the app is still mid-launch
5. XCUIApplication.terminate() cannot cooperatively terminate a not-yet-ready process → falls back to SIGKILL after a timeout → launchd catches "exec terminated before ready" → `.ips` written

Fix: after `.launch()`, poll `XCUIApplication.state` on main-actor
every 250 ms until state is `.runningForeground`, up to
`wait_for_foreground_ms` (default 15000). Return actual final state in
the outcome. Report `waitedMs` + `terminalState` on the wire.

Callers that want the pre-v1.0.11 behavior (return immediately, don't
wait) pass `wait_for_foreground_ms: 0`.

### D4 — Cumulative session lifecycle counters (§C.3)

Add to `DiagnosticSnapshot`:

```
sessionCounters: {
  openedTotal: N,      // cumulative — survives close
  closedTotal: N,
  terminateAppTotal: N,
  terminateAppViaXCUIApplication: N,   // cooperative pathway succeeded
  terminateAppViaFallback: N,          // XCUIApplication timed out; SIGKILL fallback used
  launchAppTotal: N,
  launchAppWaitedForForegroundTotal: N,
  launchAppTimedOutBeforeForegroundTotal: N,
}
```

Persist to `~/Documents/smix-session-counters.json` on every
mutation, alongside the v1.0.5 session persistence file. Rehydrate on
runner boot. `.sessionCounters.terminateAppViaFallback > 0` is the
smoking gun insight is asking for at §C.1.

### D5 — Terminate outcome detection (fix §A1 root cause visibility)

Instrument `terminateApp`:

```swift
terminateApp: { req in
  let start = Date()
  var terminatedCooperatively = false
  ...
  await SmixRunnerServer.onMain {
    let stateBeforeMs = app.state == .notRunning
    entry.app.terminate()
    // XCUIApplication.terminate() is BLOCKING — returns after the process
    // has been observed .notRunning OR after the framework's internal
    // ~30s timeout. If we're here and .state == .notRunning within a
    // reasonable window, the cooperative pathway succeeded.
    let stateAfterMs = app.state == .notRunning
    terminatedCooperatively = stateAfterMs
  }
  if terminatedCooperatively {
    counters.terminateAppViaXCUIApplication &+= 1
  } else {
    counters.terminateAppViaFallback &+= 1
  }
  ...
}
```

Consumers can now grep `.sessionCounters.terminateAppViaFallback == 0`
to confirm cooperative termination.

### D8 — RFC on the AppAliveCache invariant (§C.6)

Short standalone doc at
`.claude/rfcs/appalive-cache-invariant.md`. Explains:

- The invariant: "when the a11y tree returns `unknown` for descendants
  of the target app, suppress subsequent tree-touching requests for
  20 s so the caller doesn't retry-spam a dead app; re-probe every 3 s
  to catch a resurrection."
- What consumers see when the invariant fires: `visible: unknown` on
  the top row + all `unknown` descendants + `TIMEOUT` after 90 s.
- What consumers should do to distinguish "app really dead" from "app
  alive but a11y annotations sparse" (the dev-launcher picker case is
  the latter).
- How to observe: `diagnostic dump` counter deltas.

Not blocking on D1-D7 but ships alongside so consumers have a mental
model when they hit the symptom next time.
