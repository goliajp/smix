`docs/v2.md` 2026-07-19 的功能闭环审计末尾挂着 14 条「待办(按严重度,未修)」。抽验 5 条:

|---|---|---|
| ① `localizedText` 两 SDK 全死 | 未修 | **已修**(selector 有 `rename`/`alias`) |
| ③ MCP `ocrText` 恒假绿 | 未修 | **已修**(`ocr_text_of` 分发到 OCR 路径) |
| ④ iOS runner 无 `/input-text` | 未修 | **已修**(`InputTextRoute.swift`) |
| ② `webview_eval` 硬编码 | 未修 | **仍在**(`lib.rs:1330`) |

**5 条里 3 条已修却仍标未修,9 条状态未知。** 这份清单既高估也低估现实,而它是"v2 还差什么"的主要依据 ——

## 已知风险

- **重验会发现新的未修项**,清单只会变长不会变短。对策:C1 只求"状态准确",不在 C1 里修任何东西 ——
  边验边修会让人分不清"验完了"和"修完了"
- **`/tap` 选择器缺口(⑤)可能牵动 Swift runner 路由**,体量未知。对策:C1 产出的状态表要带
  "修它要动哪几层"的估计,让 C3 能按体量排序而不是按序号
- **范围承诺(`--stable` / MCP 两类能力)的去留是用户的决定,不是我的**(§13 + utility-judgment-is-not-mine)。
  对策:C4 只产出决策材料 —— 现状、成本、替代方案 —— **不自行实现也不自行撤回**
- **模拟器与用户工作抢资源**。对策:需要设备的核实集中在 C3,起之前 pgrep

## TDD 要点

C1 是纯核实,不写测试也不改代码 —— 它的产出是事实。
C2/C3 走红绿:先让缺口以可观察的方式变红,再修,再复跑转绿。
C4 是文档产出,无测试。

**贯穿全段的一条**:凡"已修"的判定必须给出**代码位置**作为证据,不接受"看起来修了"。
这份清单第一次失真就是因为没人回头看。
