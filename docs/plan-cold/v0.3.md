# plan-cold/v0.3 — AX 读取 + Selector Resolver

## 为什么要做
v0.2 后能"打"但不能"看"——`tap` 接受 selector 但内部还无法把 selector 解析到具体元素。v0.3 落地 AX 树读取（主 `AccessibilityPlatformTranslation` + fallback `XCUIElementSnapshot`）和完整 Selector resolver（4 base + 8 modifiers）。完成后所有 selector 形态都能找到对应元素。

## 入口条件
```bash
test -f docs/plan-history/v0.2-c7-hot.md
bun src/cli/index.ts run examples/calc-tap.test.ts  # v0.2 e2e 通
# Swift bridge 的 InputChannel 抽象在位
test -f swift-bridge/Sources/SimxBridge/InputChannel.swift
```

## 资源依赖
- 环境：与 v0.2 同
- 私有符号：`AccessibilityPlatformTranslation.framework`（host-side AX tree 读取）
- 公开 API：`XCUIElementSnapshot`、`XCUIElement.elementType`
- 外部参考：
  - Apple [XCUIAutomation framework](https://developer.apple.com/documentation/xcuiautomation)
  - WWDC25 #344 — `XCUIElementSnapshot` 行为细节
- 人 / agent：Swift bridge sub-agent 继续

## 已知风险
- **AX 树深度限制（60 层）**：RN / Flutter 嵌套深易超限。需要 flatten + 分屏 snapshot
- **`AccessibilityPlatformTranslation` 也是私有**：同 v0.2 对策，dlsym + 降级
- **相对位置 modifiers 几何计算位置**：在 Swift 侧做（避免 TS 反复 dispatch），但 Selector 本身是 TS 类型 → 通过 JSON 传协议
- **AX label / value / text 三者关系**：iOS 17 vs 26 有微差。test 矩阵要覆盖

## TDD 要点
- Swift 单测：构造已知 AX 树 → 断言每种 selector 都能 resolve 到正确节点
- TS 单测：mock driver.findOne / findAll，断言 ElementHandle.resolve 行为
- 集成：用 Calculator 和 Settings.app 两个真实场景验证 4 base + 8 modifiers 全组合
- 性能基准：100 节点的 AX 树 resolve 一个 selector P50 < 20ms

## Checkpoint 概要列表
- **C1** XCUITest snapshot 路径：通过 runner 拿到 `XCUIElementSnapshot` JSON
- **C2** `AccessibilityPlatformTranslation` host-side 直读路径
- **C3** Swift ↔ TS 的 `A11yNode` 序列化协议固化，含 `XCUIElementType` → Playwright Role 翻译
- **C4** Selector resolver 4 base（text/id/label/role+name）+ regex 支持
- **C5** Selector resolver 8 modifiers（near/below/above/leftOf/rightOf/inside/nth/first|last），含几何阈值
- **C6** SDK `findOne` / `findAll` / `waitFor` / `ElementHandle.resolve` 接通
- **C7** `examples/login.test.ts` 完整跑通（含 selector + tap + fill）
