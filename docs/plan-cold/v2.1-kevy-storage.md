# plan-cold/v2.1-kevy-storage.md — every byte smix persists moves to kevy

## 为什么要做

smix 现在有三套互不相干的持久化:smix-server 的 valkey(一个集合)、smix-server 的
postgres(一张表)、CLI 侧散落的手写 JSON 文件。三套各有各的失败模式,而其中体量最大的
一套(JSON)连原子性都没有 —— `let _ = std::fs::write(...)` 忽略返回值的写法在树里是常态,
多个 smix 进程并发时会互相截断。统一到 kevy 之后,持久化只有一处实现、一套失败语义、
一个可检视入口。

## 入口条件

```bash
cargo info kevy-embedded | grep '^version'   # 期望 3.18.0(已发布)
```
- kevy-embedded 3.18.0 已在 macOS 实测可用(`Store::open` + `set/get/flush` 通过)
- **3.18.0 的 API 与本机 workspace 的 4.0.0 不同**(无 `shutdown()`,用 `flush()`);
  一切设计对齐 **crates.io 的 3.18.0**,不对齐本机路径版本

## 资源依赖

- crates:`kevy-embedded = "3.18"`(已发布,Apache-2.0 OR MIT,与 smix 双授权兼容)
- 无需外部进程:kevy 以进程内嵌入方式运行,`Config::with_persist(dir)` 落盘
- 环境:macOS(CLI/runner 主平台)+ ubuntu(CI 的 server-integration job)

## 已知风险

- **既有用户状态**:`.smix/sims.json` 已在用户机器上。必须一次性导入,不能让升级后
  设备注册表凭空消失 → C2 内实现导入并测试
- **可读性回退**:JSON 文件今天可以直接 `cat` 出来排障(本轮我自己就靠它定位过问题)。
  KV 是二进制 → 必须提供 `smix store dump` 输出 JSON,能力不降级
- **3.18 vs 4.0 API 漂移**:本机 kevy 领先一个大版本,极易照着本机源码写出 3.18 编译
  不过的代码 → 所有 API 使用以 `~/.cargo/registry/.../kevy-embedded-3.18.0/` 为准
- **smix-server 的两个 CI service 容器**(postgres/valkey)在 C3/C4 后应当消失;若忘记
  拆除,CI 会继续绿着跑一个没人用的服务 → C5 显式检查

## TDD 要点

每个存储面先写"数据写进去、拿得回来、进程重开仍在"的测试,再实现。
删除旧实现之前,先让新实现在同一测试下通过 —— 不做"改完再补测试"。

## Checkpoint 概要列表

- **C1**:`smix-store` crate —— 唯一打开 kevy 的地方,key schema + 类型化访问 + `dump`
- **C2**:CLI 本地状态(sims / runner state / flow-attempts / capsule state)迁到 smix-store,
  含旧 JSON 一次性导入
- **C3**:smix-server 的 valkey 集合迁到 kevy,移除 `redis` 依赖与 CI valkey 容器
- **C4**:smix-server 的 postgres `stream_sessions` 迁到 kevy,移除 `sqlx` 依赖、
  migrations 与 CI postgres 容器
- **C5**:收口 —— 文档 / CHANGELOG / 新闸门(禁止再写 JSON 状态文件)/ 依赖清理 /
  CI 简化 / 真机端到端复验
