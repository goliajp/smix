# plan-cold/v2.2-android-behavioural-gate.md — Android 侧的断言必须有地方失败

## 为什么要做

07-20 到 07-21 连续三个 Android 缺陷是同一个形状：**读了参数,断在最后一跳的空实现**
(`set_force_key_events` / `set_target_bundle_id`),以及**照抄文档占位符的 view-id 拼法**
(`com.example.app:id/<tag>`,对任何真实应用都不命中)。三个都不让任何东西变红,所以都活了
下来。

根因不在这三处代码,在**没有任何闸门跑 Android 的行为**:

- CI 与 ship.sh 只跑 `:sdk:testDebugUnitTest`。**`:app:testDebugUnitTest` 无人跑** ——
  8 个测试文件(RunnerWire 编解码 / ViewIdCandidates / SessionTable / Popup / Tree),
  包括为修复上述缺陷刚写的那 5 个。
- **instrumentation 侧无人跑**:两个模块各有一份 `src/androidTest/`,但**它们不是同一种
  东西**(C2 热化时实测更正):
  - `:sdk` 是真断言 —— conformance harness(24 个 fixture,与 `crates/smix-core-conformance/`
    的那份 `diff -rq` 无差异)+ `Spike001Test`。这一份是闸门缺口。
  - `:app` 的 `RunnerTest.kt` 1241 行**不是套件,是 runner 本体** —— 只有一个 `@Test`
    (`runServerForever`),拉起 HTTP server 后永久阻塞,其余 1200 行是路由实现。它每次
    `smix runner up --platform android` 都在跑,只是不以 gradle connected 任务的形式。
    **对它要求 `connectedDebugAndroidTest` 不会失败,会永不返回** —— 照抄进 ship.sh 会让
    发布脚本永久挂起。它该不该进闸门、以什么形式,是 C3 要定的事。

iOS 侧的同型盲区已在 v2 决策日志记过两次(「ship gate 从不编译分发给用户的运行器主体」、
「stale test 潜伏 15+ 版」)。Android 侧更深一层:不是不编译,是连已经写好的测试都不跑。

## 入口条件

```bash
# 护栏就位 —— 套件跑起来之前就够不到物理手机
bash scripts/dev/adb-guard.test.sh          # 期望:all cases pass
python3 scripts/dev/workflow-scan.py        # 期望:clean
# 无人占用 Android 工具链
pgrep -fl 'emulator|mobilegate'             # 期望:空
( cd android-runner && ./gradlew --status ) # 期望:无 BUSY daemon
```

**不要用 `pgrep gradle` 判占用**:本机常驻一个 IDLE 的 Gradle daemon,它是 wrapper 的
正常产物,那条命令永远非空,照它执行会每次误判成"有人在跑"。

- adb-guard 已 wire 并被 workflow-scan 盯住(2026-07-21 已完成)
- 已知 `:app:testDebugUnitTest` 当前为绿(本机实测),即 C1 是接线而非修测试

## 资源依赖

- 环境:Android SDK + `sim-smix-android-01` emulator(memory: simx_android_emulator_setup);
  JDK + gradle 9.3.1(仓库自带 wrapper)
- **`ANDROID_SERIAL=emulator-NNNN` 必须显式钉住** —— gradle 的 install/connected 任务会
  扇出到每一台连着的设备,adb-guard 会拦下没钉的调用
- CI:instrumentation 需要 emulator runner,GitHub hosted runner 上是否可跑属 C3 的判定项,
  不预设

## 已知风险

- **从未被跑过的断言大概率 stale**。对策:C2 只求「编译 + 跑通 + 如实记录通过率」,修测试
  是 C2 内的独立步骤,不与接线混在一起;每修一条要说清它当初为什么 stale(产品变了 vs
  测试写错),**不允许为了绿而删测试**
- **`:sdk` 的 `ConformanceHarnessTest` 设计上恒 pass**(注释明写 "Always pass — test is an
  emit harness")。对策:C2 的通过率必须能与 `OK (0 tests)` 区分 —— 验收断言具体的 tests 数,
  不只看 failures=0
- **emulator 与用户其它工作抢资源**(memory: 起服务前先 pgrep user build)。对策:每次起
  emulator 前 pgrep;真跑让位活动 batch
- **物理手机在场** —— 这不是假设:C2 热化时实测 `adb devices` 列着 `R5CT52DF07D`
  (USB + 无线两条),且当时没有任何 emulator 在跑。**不钉住的设备变更命令现在就会打到
  用户的手机上**(已因此擦过一台 SM-S9010)。对策:adb-guard 是硬前置;且它判的是**单条
  命令的文本** —— `export ANDROID_SERIAL=` 写在另一条命令里它看不见,必须内联前缀
- **CI 上 instrumentation 可能跑不动** → 若如此,必须**明说降级到哪一层**并写进 gate 输出,
  不允许静默只跑单测却让人以为 Android 被覆盖了

## TDD 要点

这一段的被测对象是**闸门本身**,不是产品代码。每个 checkpoint 的验证形态固定:先证明闸门
在缺陷在场时会红(注入或用真实的历史缺陷),再接线,再复跑转绿。C4 是唯一涉及产品行为的
一段 —— 那里走真设备实测,不是红绿。

装回缺陷版本时该断言会红。
