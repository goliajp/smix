# plan-cold/v2.5-release-record.md — 发布记录必须说得清这次发布是什么

## 为什么要做

v2.0.0 是第一个对外正式发布,而**两份告诉别人「这次有什么破坏性变更」的清单已经互相对不上**:

- `docs/v2.md` 「六项破坏性变更」表:**6 行**
- `CHANGELOG.md` `## [2.0.0]` 的 `### Breaking`:**8 条**

多出的两条(smix-server 去数据库、选择器映射拒未知键)是真的破坏性变更,只是从没回填进
`v2.md` 的表 —— 而 CLAUDE.md §10 写着「版本边界改动 → 改 `v2.md`,不在 plan 里偷偷加」。

更要紧的是 **v2.1–v2.4 四段各自又引入了破坏性变更,两份清单都不知道**:

| 改动 | 表面 | 谁会被打断 |
|---|---|---|
| `DeviceControl::launch_with_args` 加 `activity` 参数 | `smix-sdk` 公开 trait | 自己实现该 trait 的调用方 |
| `LaunchAppOptions` 加 `launch_activity` 字段 | `smix-sdk` 公开结构体 | 用字面量构造它的调用方 |
| `Flow` 加 `launch_activity` 字段 | `smix-adapter-maestro` 公开结构体 | 同上 |

三条都发生在 v2.0.0 发布**之前**,所以并入 v2 major 是对的;
**但没被记下来这件事本身不对** —— 发布说明是用户唯一能读到的东西。

这一族与 v2.1–v2.4 收掉的是同一个物种:**写下时为真、之后失真、中间无人看守**。
前四段管的是代码与指南,这一段管的是**发布记录本身**。

## 入口条件

```bash
bash scripts/dev/preflight.sh            # 期望:preflight: clean
test ! -f docs/plan-hot.md               # 期望:成立
cargo test -p smix-cli --bin smix guide_gate -- --nocapture 2>&1 | grep 'guide-executability:'
# 期望:8 claims (8 runs / 0 broken / 0 unjudged) —— v2.4 已收口
grep -c '^| [0-9] |' docs/v2.md          # 六项破坏性变更表的行数
awk '/^### Breaking/,/^### Added/' CHANGELOG.md | grep -c '^- '
# 两个数字对不上,就是本段要闭的第一条
```

## 资源依赖

- 无需设备。全段静态可判定
- `cargo-semver-checks` 已是 C18 的 ship gate;本段**不**把它搬进 preflight
  (它要拉上一版的 registry 元数据,慢且需要网络)——本段只保证**记录**与**决策日志**一致

## 已知风险

- **「破坏性变更」的边界靠人判**。加一个 `pub` 字段是不是破坏,取决于结构体是否 `non_exhaustive`、
  调用方是否用字面量构造。对策:判据写死在闸门的 docstring 里,**并明写闸门不判这个** ——
  它只判「两份清单一致」,不判「这一条是不是真的破坏性」
- **CHANGELOG 的 `Added` / `Fixed` 覆盖度机器判不了**。对策:C1 只做 `Breaking` 的双向对账
  (那一节的条目有稳定形状);覆盖度留给 C2,判据等 C1 的结果出来再定 ——
  与 v2.4 冷计划同一处理
- **清单会变长**。v2.1–v2.4 的三条只是我这次翻出来的;回填时可能发现更多。
  这不是风险,是这一段存在的理由

## TDD 要点

闸门先于回填:先让它对着现状变红(两份清单行数与内容都对不上),再回填到绿。
每条回填都要能在删掉时重新变红。

## Checkpoint 概要列表

- C1:`docs/v2.md` 破坏性变更表 ↔ `CHANGELOG.md` `### Breaking` 双向对账闸门 +
  把两份清单都补全(含 v2.1–v2.4 引入的三条)
- C2:`CHANGELOG.md` 的 `2.0.0` 段覆盖 v2.1–v2.4 实际做过的事;覆盖判据由 C1 的结果定
- C3(条件性):若 C1/C2 翻出发布前必须回答的问题(例如某条破坏性变更需要迁移说明而
  `smix migrate` 覆盖不到),逐条闭合

## 出口验收

```bash
cargo test -p smix-cli --bin smix release_record
bash scripts/dev/preflight.sh
```

三条 v2.1–v2.4 引入的破坏性变更在两处都有;每条都能在删掉时让闸门变红。

**不在出口内**:`docs/scope-decisions-pending.md` 里三条待拍板(`--stable` /
MCP `diagnostic-dump` / MCP `session`)。那是委托方的决定,**这一段不绕过它们,也不替它们做**。

## 触发热化的 prompt 模板

按 CLAUDE.md §6 标准模板,附加本段专属 context:

- 必读:`docs/v2.md` §六项破坏性变更 与 `CHANGELOG.md` `## [2.0.0]` 的 `### Breaking`
- 必读:v2.1–v2.4 四段的决策日志(它们是这三条破坏性变更的一手记录)
- 硬约束:闸门只判两份清单是否一致,**不判某条是不是真的破坏性** ——
  后者是判断,写进 docstring 的「看不见什么」
