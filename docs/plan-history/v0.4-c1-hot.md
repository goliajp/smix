## 5 决策答案

### 决策 1：`visible` 过滤算法

**答**：`node.visible === true && node.enabled === true`（同 `collectVisibleSummaries` 既有逻辑，简单复用）。

理由：
- v0.3 C1 已落 `TreeRoute.isVisible(frame:appFrame:)` 启发式（frame ∩ appFrame 非空 && 非零；详 `design.md` §A11yNode wire 协议 line 361）。`A11yNode.visible` 字段已是固化 wire 字段，重新算几何属于重复工作。
- 加 `enabled === true` 过滤掉 disabled separators / 非交互 wrapper（match 既有 `collectVisibleSummaries` 行为，line 474 `simctl-driver.ts`）；matcher 失败提示给 AI 的元素列表应当是"AI 可以选择 tap 的可用候选"。
- 拒绝"只 frame 非空"候选：(1) 复制 C1 的 isVisible 逻辑会让 wire 字段失去单一信任源；(2) bounds 字段 wire 上保证存在（`A11yNode.bounds` 必填），但 `visible: false` 的节点也可能 bounds 非空（被遮挡 / 屏幕外内但 frame 自己非零）—— `visible` 字段才是"可见性"权威。

### 决策 2：elements 排序

**答**：DFS pre-order（与 C4 `resolveSelector` first-match-wins 同序）。

理由：
- 与 v0.3 C4 决策同语义（DFS pre-order，`design.md` §搜索顺序）；selector matcher 的 "first-match-wins" 与 visibleElements 列表序一致 → AI 看 prompt 时能直觉对应到 "resolver 优先看到的元素"。
- 既有 `collectVisibleSummaries` (line 468 `simctl-driver.ts`) 已是 DFS pre-order；保持一致避免两套语义。
- 拒绝"bounds top-to-bottom + left-to-right"：(1) 多加排序 O(N log N) 与 v1.md §4 [3] 5s 冷启动延迟预算同向；(2) iOS sim 上 navigation bar / status bar 总占 top 行，会把无关元素挤到前面；(3) DFS 序反映 a11y 树语义层级（cell > button > label），AI 对树形更敏感于像素位置。
- 拒绝"按 hit-test 优先级"：`ScreenDescription.elements` 的 JSDoc 说 "sorted by hit-test priority"（screen.ts line 49）—— 但 hit-test priority 实际等价于 DFS pre-order 反向（iOS 子视图在父视图上）。v0.4 C1 不引入反向遍历（与 resolver 不一致代价大）；JSDoc 留待 v0.4 C8 / v1.1 时若 VLM 需要可改"DFS pre-order"。

### 决策 3：top N 截断

**答**：**50**（与 `plan-cold/v0.4.md` 风险段字面对齐 + 留 edit-distance 算法空间）。

理由：
- `plan-cold/v0.4.md` line 21 显式记 "edit-distance 在大量元素时慢：限 top 50 visible 元素再算"。决策对齐冷计划。
- `error.ts` `toPrompt()` 只渲染 top 10（line 73 `Math.min(10, this.visibleElements.length)`）—— UI 给人看的是 10；但 `ExpectationFailure.visibleElements` 给 AI 喂的（trace `failure.json`）应当宽（C4 写 jsonl）。50 是 toPrompt 10 + edit-distance candidates 头部 40 的合理 union。
- 拒绝 10：(1) 偏少，AI 拿 `failure.json` 做"修 selector"时缺候选；(2) `buildSuggestions` (matchers.ts line 197) 用 top 3 + similarity > 0.6，下游处理已自带二次截断。
- 拒绝 100：(1) snapshot 60 层 + 单层 ~10-30 个 visible 节点 → typical 100-300 visible，100 不够 saving，50 是 noise/signal 拐点；(2) wire JSON 大小 50 × ~80 bytes = 4KB（写 trace + feed 回 AI 都合适）；100 × 80 = 8KB 开始影响 toPrompt 输出体积。
- 现有 `collectVisibleSummaries` 在 `tapViaResolver` 上 limit=10（line 283）是"tap not-found 错时给的少量上下文"；matcher 失败上下文 limit=50 是"feed 回 AI 全量"。两个 limit 不同合理（不复用同一常量）。

### 决策 4：`summary` 字段

**答**：**不填**（保留 `''` 空字符串，与 v0.4 C1 范围外）。

理由：
- `plan-cold/v0.4.md` 7 checkpoint 列表（line 33-40）未提 `summary` 填充；`summary` 在 `v1.md` §2.D MCP 段对应 `explain_screen` tool（"子进程调本机 `claude -p ... --image ...`"，line 49）—— 走 VLM/Claude CLI 路径。
- v1.md §3 边界表 "Vision OCR / 视觉兜底 → v2"（line 68）—— `summary` 1 句话不可能不调 VLM，规则 templating 没语义。
- C1 范围严格："matcher 失败时 visibleElements 字段真填充"—— 单职 1 件事，添加 summary 是 scope creep。
- 现 `safeDescribe` 调 `driver.describe()` 后只读 `screen?.elements`（matchers.ts line 131）—— 不读 summary 字段，加了也不消费。
- v0.4 后续 / v2 集成 VLM 时再补；schema 字段已存在不破契约。

### 决策 5：`frontApp` 字段

**答**：**保持现状 = `lastLaunchedBundleId`**（不读 tree.identifier）。

理由：
- v0.3 C1 决策日志（`v1.md` line 139）明确："XCUIApplication.snapshot() 根 identifier 是空——UITest closure 加 `rootIdentifierOverride: bundleId` 参数补"。换句话说，**runner 侧的 tree root identifier 已经是 bundleId**（如果有），但通过 `RunnerClient.getTree()` 取到的 root.identifier 是从 runner 接到的 launchedAppId echo，**不**比 host-side `lastLaunchedBundleId` 更可靠（runner 与 host 是同 PID 内 closure，bundleId 同源传递）。
- v0.2 C6 `lastLaunchedBundleId` 在 `launch()` 末尾真填（line 138 `simctl-driver.ts`）—— 这是 v0.2 已锁定的 v0.4 C1 不再 retrofit 它；已写真值，不需要 second source。
- 拒绝读 `tree.identifier`：(1) tree root identifier 在 iOS 26.4 sparse-tree regression 下可能持续空（v1.md line 144 v0.3 C6 决策日志：sparse-tree 时 root identifier 为空），即使 sparse 不退 visibleElements；(2) `tree()` 拉的 latency vs `lastLaunchedBundleId` 内存读 = ms vs 0；C1 用户调 `describe()` 已经付 1 个 tree 拉的代价，没必要在同一调用内 conflict source。
- 边界 case：如果用户切了 app（v0.2 doesn't 真实做 multi-app launch，但理论上可），`lastLaunchedBundleId` 是 stale—— 这是 v1.md §2.D MCP `screen_describe` 一等公民时再处理（"AI 主动调 describe 来检测当前 app"），v0.4 C1 不修。
- v0.7+ HID 键盘 + runner lifecycle 时如果引入 `app.background()`/`foreground()`，再修 frontApp 真相。

### Step 1：`SimctlDriver.describe()` 真填 elements

- `summary: ''` 不变（决策 4）。`frontApp: this.lastLaunchedBundleId ?? ''` 不变（决策 5）。

`describe()` 新逻辑（伪代码）：
```ts
async describe(): Promise<ScreenDescription> {
  return this.wrap('describe', async () => {
    const png = await this.session.client.screenshot(this.session.udid)
    let elements: ElementSummary[] = []
    try {
      if (this.treeSource !== undefined) {
        const tree = await this.tree()
        elements = collectVisibleSummaries(tree, 50)
      }
    } catch {
      // tree unavailable (no runner / sparse-tree / transport fail) →
      // describe() must still return a usable ScreenDescription; an empty
      // elements list is the documented degraded mode (matchers will fall
      // back to a bare suggestions-less prompt, same as v0.3 pre-C1).
      elements = []
    }
    return {
      screenshot: png.toString('base64'),
      elements,
      frontApp: this.lastLaunchedBundleId ?? '',
      summary: '',
      capturedAt: Date.now(),
    }
  })
}
```
