## 目标 checkpoint

**C3：`ExpectationFailure.suggestions` 是基于 (name + label + value) 多字段 token-aware edit-distance 排序的 top-3 候选字符串，且 `toPrompt()` 将其作为 AI 可消费的 "Did you mean ..." 段渲染。** 通过后世界变成：

- AI 拿到 `failure.json` / `toPrompt()` 输出，能在不看 visibleElements 大列表的前提下，从 suggestions 直接读到"最像的 3 个真实元素文本"（含相似度小数和参与匹配的字段名）。

## 关键发现（基于现状代码精确引文）

### F1. `buildSuggestions` 当前实现 (matchers.ts line 212–220) 的 5 个实际不足

```ts
function buildSuggestions(handle: ElementHandle, visible: ElementSummary[]): string[] {
  const target = extractTargetString(handle)
  if (!target) return []
  const lower = target.toLowerCase()
  const matches = visible
    .filter((el) => el.name && similarity(el.name.toLowerCase(), lower) > 0.6)
    .slice(0, 3)
  return matches.map((m) => `Did you mean ${JSON.stringify(m.name)}? (similarity ${similarity(m.name!.toLowerCase(), lower).toFixed(2)})`)
}
```

不足：

1. **仅比 `el.name`**：`ElementSummary` (screen.ts line 36–43) 有 `{role, name?, id?, text?, bounds, enabled}` —— `text` 字段（label 与 name 不同时填）完全不参与；多字段 typo 命中率打折扣。
2. **未排序**：`.filter(...).slice(0, 3)` 取的是 visible 列表 **DFS pre-order** 的前 3 个相似项（C1 决策 2），不是 **相似度最高** 的 3 个 —— 真实 typo 可能命中第 5/8/15 个 visible，被前面 3 个低分项挤掉。
3. **阈值 0.6 拍脑袋**：单字符 typo "Sgin in" (7 chars) → "Sign in" 距离 2 → similarity = 5/7 ≈ 0.714 (pass)，但大小写漂移 "general" (7) → "General" 距离 1 → similarity = 6/7 ≈ 0.857（如果先 lowercase）—— 当前已 lowercase compare，case 不是问题；问题是阈值 0.6 让 "Sgni" vs "General" (distance 5/7 → 0.286) 安全过滤掉，但 "Cancl" (5) vs "Cancel" (6) → distance 1/6 → 0.833 pass，**与** "Cancl" vs "Continue" (8) → distance 7/8 → 0.125 fail —— 阈值合理范围 0.5-0.7 实测 0.6 是 ok，但**未文档化为决策**且未在测试覆盖边界。
4. **`extractTargetString` 仅看 selector 4 字段中前 3 个**（line 222–228）：`text → label → name`。**漏 `id`**（`BaseId = { id: string }`）—— 当 AI 写 `app.element({ id: 'genral-cell' })` 错 typo → suggestions 全空。但 `id` 是 `identifier` 严格 case-sensitive（v0.3 C4 决策日志 v1.md line 142），不参与 fuzzy。决策 3 见。
5. **相似度小数 `.toFixed(2)`** 在 message 内，但 message 是非结构化字符串 —— AI 解析需要正则。Message 形态保留 (Playwright-likeness)，但同时把 `similarity` 数字嵌得稳定（前缀 `(similarity ` 固定）使 AI 可正则 `similarity (\d\.\d{2})` 解。

### F2. `extractTargetString` 行为细节 (matchers.ts line 222–228)

- `selector.text` 可能是 `string | RegExp`（`BaseText` 定义 selector.ts line 18）—— 当前实现 `typeof s.text === 'string'` **正确**屏蔽 RegExp（RegExp typo "建议" 无语义）。
- `selector.label` 是 `string`，`selector.name`（role+name 中的 name）是 `string | RegExp` 同理需 type guard。
- `selector.id` 当前**未提取**（决策 3 见）。

### F3. `similarity` / `editDistance` 算法正确性 (matchers.ts line 230–253)

实测推演：

- `similarity('sgin in','sign in')`：longer=7, distance=Levenshtein('sgin in','sign in')。'sgin' vs 'sign' 是单 swap (2-char transposition) 但 Levenshtein 没 Damerau swap → 2 substitutions（'g'→'i', 'i'→'g'）= **distance 2**。similarity = (7-2)/7 ≈ 0.714 > 0.6 ✓
- `similarity('general','General')`：先 lowercase 都是 'general' → distance 0 → similarity 1.0 ✓
- `similarity('genral','general')`：longer=7, 漏 e → distance 1 → similarity 6/7 ≈ 0.857 ✓
- `similarity('','')`：special-case `longer.length === 0` → 1 (但不会进 filter 因为 visible.name 非空保证 ≥1 char)
- `similarity('a','xyzabc')`：longer=6, shorter='a', distance=5 → 1/6 ≈ 0.167 < 0.6 → filter out ✓

**结论**：`similarity`/`editDistance` 内部 OK，不需重写；C3 改写 `buildSuggestions`（外层 ranking + multifield + threshold 文档化）和 `extractTargetString`（加 id？决策 3）即可。

### F4. `ExpectationFailure.toPrompt()` 当前 (error.ts line 58–83) **不渲染 suggestions**

```ts
toPrompt(): string {
  const lines: string[] = []
  lines.push(`FAIL [${this.code}]: ${this.message}`)
  if (this.selector) lines.push(`  selector: ${describeSelector(this.selector)}`)
  if (this.visibleElements.length > 0) {       // ← visible elements 段
    lines.push(`  visible elements (top ${Math.min(10, this.visibleElements.length)}):`)
    for (const el of this.visibleElements.slice(0, 10)) lines.push(`    - ${renderElement(el)}`)
  }
  if (this.hint) lines.push(`  hint: ${this.hint}`)
  return lines.join('\n')
}
```

**`this.suggestions` 字段从未读**。这是 v0 时期遗留 — error.ts 与 matchers.ts 在 v0 同期写，`suggestions` 字段先建好但渲染推到 v0.4 真接通后才补。C3 必须补，否则"接通"只完成 50%（数据填了但 AI 看不到——`failure.json` 内 `toJSON()` 写 `suggestions` 数组 ✓，但 `toPrompt()` 给 stdout / Claude prompt feed 用 0 ✗）。

## 7 决策答案（含拒绝路径，每条必答）

### 决策 1：比较字段范围

**答**：`name + text` 两字段（label 通过 summarizeNode 收敛到 name，不重复参与）。

理由：

- `ElementSummary` (screen.ts line 36-43) 字段：`role / name? / id? / text? / bounds / enabled`。其中 `name` 由 `summarizeNode` (line 64) 装载 `node.label ?? node.text ?? node.value`，`text` 仅当 `node.text` 与上面填的 name 不同时存在（line 67 `if (node.text && node.text !== summary.name) summary.text = node.text`）。
- 因此**"label 单独参与匹配"等于 name 已经覆盖**（除非 cell 同时有 label + 不同 text，此时 text 单独参与有意义）—— `name + text` 已穷尽所有可比文本信号，不需要单独 label 字段（label 已经收敛到 name）。
- `value` 不直接出现在 `ElementSummary` —— 已被 summarizeNode 收敛到 `name`（同字段 fallback chain）。所以"扩展到 (name + label + value)"在 ElementSummary 抽象下等价于 `name + text`，与"只比 name"差在 text 字段是否参与。
- 拒绝（A）"仅 name"：iOS sim Settings 上观察 cell>button 形态时，cell.label 与 button.label 不同（v0.3 C1 决策日志 v1.md line 139 提及 "Settings cell 实际 layout 是 `cell` 包 `button` (button.label='General')，不是 `cell.label='General'`"），summarizeNode 把 button.label 装到 button summary 的 name，cell summary 的 name 可能是空或 cell raw 名 —— `text` 字段在某些 native iOS 17/18 layout 上会承载 "Static Text" 节点的实际显示文本而 name 是空。漏比 text 会丢一类 case。
- 拒绝（B）"扩展到 raw a11y node 4 字段 (label/value/text/identifier)"：违反"不改 ElementSummary schema"硬约束（决策 0 范围），且 identifier 是 strict equality 不 fuzzy（v0.3 C4 决策日志 v1.md line 142 "id 严格 case-sensitive 相等于 identifier"）。
- 拒绝（C）"name + text + id"：id (identifier) 是程序化句柄，case-sensitive 不该 fuzzy（如 `genral-cell` vs `general-cell` 是 1 char typo 但 BaseId selector 语义本来就要求严格相等；fuzzy 建议反而误导 AI 写错的 strict-match selector）；id 进入 suggestions 会让 AI 困惑"为啥它建议这个 id 但 strict id selector 又不匹配"。

实操：`candidates = [summary.name, summary.text].filter(Boolean)`，每个 candidate 独立算 similarity，取**最高分**做该 element 的 score，**记录命中字段**（'name' / 'text'）用于 suggestion message。

### 决策 2：selector 端取串

**答**：从 selector 取 fuzzy 比对源 = `{ text, label, name (in role+name) }` 三字段，**string 型才取**（RegExp 跳过）；`id` **不参与** fuzzy。

理由：

- 现行 (matchers.ts line 222-228) 已是 text → label → name 顺序 + `typeof === 'string'` guard，**保留**（C3 不为它涟漪）。
- 拒绝（A）"加 id 参与 fuzzy"：与决策 1 拒绝（C）同理 — id 是 strict-match selector 语义，fuzzy suggestion 反向（用户既已使用 id selector，typo 的 fix 是字符级别修，不是"换一个相似的 id 当 suggestion"，那个 suggestion 本来就是另一个 element）。即便要修 id typo，AI 看 visibleElements 段中每行 `renderElement` 已输出 `id="..."` (error.ts line 122)，AI 可自己肉眼比对。
- 拒绝（B）"role+name 中 role 也参与"：role 是枚举（'button' / 'cell' / ...）不是自由文本，typo `'buton'` Levenshtein vs 'button' 距离 1 但 Role 类型应当编译期防住；C3 不为运行时 role 字符串容错。
- 拒绝（C）"selector 多字段时拼成一个 target"：复合 selector 如 `{ text: 'Generl', below: { text: 'Settings' } }` 只取 base `text='Generl'` 即可，`below.text` 是 anchor 不是匹配目标 —— 当前实现已是"取 base 字段"，C3 保持。

### 决策 3：阈值 + 排序策略

**答**：

- 阈值 = **0.5**（从 0.6 降）—— 单字符 typo 在短 target (≤5 chars) 更宽容，且 0.5 在 short target 下不噪音泛滥（5-char target 至多 distance 2 即过线）。
- **主排序 = similarity 降序**；**次序 = 命中字段优先级 (name > text)**；**三序 = element DFS pre-order 索引升序**（visible 数组天然顺序，与 C1 决策 2 / v0.3 C4 first-match-wins 一致）；**截取 = top 3** 输出（保留现行）。
- **不引入** "visible 优先 / 文本长度近 target 长度优先" 等二次启发式（决策 4 见拒绝路径）。

理由：

- 阈值 0.5 vs 0.6 vs 0.7 实测推演（短 target 4-7 chars）：
  - target='Sign in' (7) vs 'Sgin in' (7) typo: similarity 0.714 → 三档全过
  - target='General' (7) vs 'Genral' (6) typo: 6/7 ≈ 0.857 → 三档全过
  - target='Wi-Fi' (5) vs 'WiFi' (4) typo: longer=5, distance 1, similarity 4/5 = 0.8 → 三档全过
  - target='OK' (2) vs 'Cancel' (6) **不应**建议：similarity = 0/6 = 0.0 → 三档全 filter ✓
  - target='Cancl' (5) vs 'Cancel' (6) typo: longer=6, distance 1, similarity 5/6 ≈ 0.833 → 三档全过
  - target='Setting' (7) vs 'Settings' (8) typo: longer=8, distance 1, similarity 7/8 = 0.875 → 三档全过
  - **边界 case** target='Setings' (7) vs 'Settings' (8) typo (漏 t): longer=8, distance 1, similarity 0.875 → 全过
  - **关键** target='Cnl' (3) vs 'Cancel' (6) → longer=6, distance 3, similarity 3/6 = 0.5 → 0.5 阈值边界刚刚过（决策 3 选 `> 0.5` strict），0.6 阈值 fail
  - 0.5 vs 0.6 的差别集中在"target 是 truncation of real label 一半"的 case；这种 case AI 极度欠信息时确实需要 suggestion。
- **次序 'name > text'**：name 是 a11y 树主标签（cell/button 的 label），text 是 staticText 节点 raw 文本 —— 同分时 name 命中比 text 命中更确定（少误判 wrapper-vs-content 的 text 漏）。
- **三序 DFS pre-order 升序**：当 score + 字段都同分，列表序确定，跨次重跑结果稳定（C8 dogfood claude -p regression 需要确定性 expected output）。
- 拒绝（A）"按 element bounds top-to-bottom 排"：(1) iOS sim status bar / navigation bar 永远占 y 最小，会把状态栏 element 推前；(2) bounds 排序 O(N log N) 与 v1.md §4 [3] 5s 冷启动延迟同向；(3) AI 看 suggestions 已经只 3 行，bounds 序对人/AI 都无差。
- 拒绝（B）"按 `target.length` 与 candidate.length 差的绝对值升序作 tie-break"：似 Levenshtein 已隐含长度差（distance 自然包含 insertion/deletion 数）；额外 tie-break 引入歧义。
- 拒绝（C）字典序 tie-break：违背"DFS pre-order 与 visible 列表同序"原则；字典序在 e2e 上 'About' 永远排前 'General'，与 Settings 屏幕实际从上到下序冲突，AI 直觉对错位。
- 拒绝（D）阈值 0.7：太严，"Setings"(7)→"Settings"(8) 0.875 pass，但 "Genrl"(5)→"General"(7) longer=7 distance 2 similarity 5/7 ≈ 0.714 → 0.7 边界过；现实 AI typo 多分布在 0.55-0.85，0.7 砍掉一半 useful suggestion。
- 拒绝（E）阈值 0.6：现行值，但实测对"3 char 短 target" 太严（target='Cnl' → 'Cancel' 0.5 < 0.6）；改 0.5 才包住短 target。

### 决策 4：toPrompt 渲染策略

**答**：渲染。`toPrompt()` 在 `this.suggestions.length > 0` 时输出：

```
  suggestions:
    - <message-1>
    - <message-2>
    - <message-3>
```

位置 = 在 `selector` 段之后、`visible elements` 段之前（让 AI 先看高密度建议，再看大列表）。缩进 = 2 空格段头 + 4 空格 item（与 visible elements 段同形态）。

理由：

- F4 已证 `toPrompt()` 当前不渲染 —— 必须补，否则"接通"只完成 50%。
- 顺序：FAIL → selector → **suggestions** → visible elements → hint。suggestions 在 visible 之前，理由 = (a) AI 优先读简短信息，(b) AI 已有 suggestions 时往往不需要看 visible 大列表，省 token。
- 拒绝（A）"加在 visible elements 之后"：AI 上下文窗口长时 suggestions 可能被 visible 列表淹没；suggestions 是高 actionability 信号，前置。
- 拒绝（B）"也加 message 渲染到 toJSON"：`toJSON()` 已经 `suggestions: this.suggestions` 字面输出（error.ts line 94），AI 拿 JSON 就有结构化数组 —— `toPrompt()` 是 stdout / Claude prompt 用，渲染必要；JSON 端不需改（schema 已对）。
- 拒绝（C）"不渲染，仅 toJSON 持有"：违反"接通"语义；CLI 跑测试失败时 stdout 是 `toPrompt()` 输出（src/cli/commands/run.ts），AI 在终端 / CI log 上读不到 suggestions = 任务未完成。

```ts
type SuggestionCandidate = {
  readonly summary: ElementSummary
  readonly field: 'name' | 'text'
  readonly value: string
  readonly score: number
  readonly index: number  // visible-array DFS pre-order index
}

const SUGGESTION_THRESHOLD = 0.5
const SUGGESTION_TOP_N = 3

function buildSuggestions(handle: ElementHandle, visible: ElementSummary[]): string[] {
  const target = extractTargetString(handle)
  if (target === undefined) return []
  const lower = target.toLowerCase()
  const candidates: SuggestionCandidate[] = []
  for (let i = 0; i < visible.length; i++) {
    const el = visible[i]!
    // name 优先，text 次（决策 1）。同一 element 两字段都参与但仅保留高分项。
    let best: { field: 'name' | 'text'; value: string; score: number } | undefined
    if (typeof el.name === 'string' && el.name.length > 0) {
      const s = similarity(el.name.toLowerCase(), lower)
      if (s > SUGGESTION_THRESHOLD) best = { field: 'name', value: el.name, score: s }
    }
    if (typeof el.text === 'string' && el.text.length > 0) {
      const s = similarity(el.text.toLowerCase(), lower)
      if (s > SUGGESTION_THRESHOLD && (best === undefined || s > best.score)) {
        best = { field: 'text', value: el.text, score: s }
      }
    }
    if (best !== undefined) {
      candidates.push({ summary: el, field: best.field, value: best.value, score: best.score, index: i })
    }
  }
  candidates.sort((a, b) => {
    if (b.score !== a.score) return b.score - a.score          // 主：similarity desc
    if (a.field !== b.field) return a.field === 'name' ? -1 : 1 // 次：name > text
    return a.index - b.index                                    // 三：DFS index asc
  })
  return candidates.slice(0, SUGGESTION_TOP_N).map((c) =>
    `Did you mean ${JSON.stringify(c.value)}? (similarity ${c.score.toFixed(2)}, field ${c.field})`,
  )
}

function extractTargetString(handle: ElementHandle): string | undefined {
  const s = handle.selector as Record<string, unknown>
  if (typeof s.text === 'string') return s.text
  if (typeof s.label === 'string') return s.label
  if (typeof s.name === 'string') return s.name
  return undefined  // id-only selector / RegExp selector → no fuzzy
}
```
