## 与冷计划假设不符之处

- **关键：C2 的 `Spawner` 类型不足以承载 C3 的两类新需求**：
  - `simctl io <udid> screenshot --type=png -` 走 stdout 二进制 PNG，C2 `Spawner` 把 stdout 类型为 `string` 会导致字节经 UTF-8 解码损坏 → **决策：新增 sibling `BinarySpawner`**（stdout: Buffer），通过 `SimctlClientOptions.spawnBinary` 注入；`defaultSpawnBinary` 用 `child_process.spawn`（非 `execFile`）拼 Buffer chunks
  - `simctl pbcopy <udid>` 走 stdin 文本注入 → **决策：扩展 `Spawner` 第 3 参为 `opts?: { stdin?: string; env?: Record<string, string> }`**（向后兼容：C2 既有 fake `async (cmd, args) => ...` 因 TS 函数参数 bivariance 依然类型兼容；C2 真实调用未传第 3 参也仍合法）。`env` 同时承载 `launch` 的 `SIMCTL_CHILD_*` 注入需求，避免 spawner 类型再扩
  - 决策原因：sibling 拆分（二进制）+ 同函数加可选参（stdin/env）= 最小变更面 + 不破坏 C2，比"在 `Spawner` 上让 stdout 同时支持 `string | Buffer`"更类型安全。
- 冷计划 C3 仅笼统列 `permissions`，未限定子集。本热计划把 `SimctlPermission` 枚举锁定到 `simctl help privacy` 实际打印的 service 集合（含 `'photos-add'`、`'siri'`、`'location-always'`，与上游一对一），未来 v0.7+ 若 simctl 增减 service 需同步本枚举。
- 冷计划 C3 列出 `appearance`，子命令归属未明示。本机探测确认走 `simctl ui <udid> appearance <mode>`（不是顶级子命令）→ 错误消息 op 字串写为 `ui appearance` 以保留诊断信息。
- 冷计划"已知风险 / boot 是异步"建议用 `bootstatus -b` 轮询。本热计划范围内 `SimctlClient.boot` **不**做 boot 完成轮询（仅发起 boot 命令），由 C4 `SimSession` 层负责调用 `bootstatus`。理由：C3 的目标是"包装"，不引入生命周期判断。`bootstatus` 不在本 C3 11 方法清单内，记录在此供 C4 参考。
- 冷计划入口条件期望 `xcrun simctl list runtimes -j | jq '.runtimes | length' ≥ 1`，本机 `platform=="iOS"` 仅 1 个（iOS 26.4），与 v1 SuccessCriteria[6]（iOS 17.5 / 18.4 / 26.x 兼容）不符 → 留给 v0.7 CI 矩阵或单独安装步骤解决；C3 单测全 mock 不受影响。
- `bun -v` 1.3.13、`xcodebuild -version` 26.4.1，均符合冷计划入口条件。
