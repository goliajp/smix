### F3. `recordStep` 内部 (run.ts line 148–169)

```ts
private async recordStep(
  type: string,
  args: unknown,
  ok: boolean,
  start: number,
  err?: string,
): Promise<void> {
  const sink = getTraceSink()
  if (sink === undefined) return
  try {
    const rec: StepRecord = { ... }
    await appendStep(sink, rec)
  } catch {
    // fs errors silenced
  }
}
```

**C5 改造**：(a) `appendStep` 返回 seq 后，recordStep 拿到 `seq: number | undefined` 返回给 caller；(b) caller (23 mutating wrap) 拿到 seq 后**单独**调 `this.captureStepPng(seq)` 用 base.screenshot()——为何拆开：错误处理边界清晰（jsonl 写盘 fs 错 vs screenshot 抛错 silent 是两类失败，统一 try/catch 会把"截屏抛错"误归"trace 写盘 fs 错"）。`screenshot` 自身的 wrap **跳过** captureStepPng（决策 3）。

### F4. `simctl-driver.ts` `screenshot()` 行为 (simctl-driver.ts line 201–205 + sim/simctl.ts line 204–221)

```ts
async screenshot(): Promise<Buffer> {
```

### F6. 文件名冲突分析

| 文件名族 | 来源 | seq 来源 | 引入版本 |
|---|---|---|---|
| `<NNNN>-screenshot.png` | 用户 `app.screenshot()` | TracingDriver.seq (内部) | v0.2 C6 |

### F7. seq 1:1 对齐机制

C4 后 `appendStep` 内部 `next = (stepSeqByCase.get(slug) ?? 0) + 1; stepSeqByCase.set(slug, next)`，写入行 `seq: next`。**该数字不暴露给 caller**——这是 C5 必须打开的口。

最小改动方案：`appendStep` 改返回 `Promise<number>` 直接返回它写入的 seq；recordStep 透传 `number | undefined`；TracingDriver mutating wrap 拿到 seq 后调 `writeStepPng(sink, seq, buf)`。这样 jsonl 行 `seq=5` 与 `step-0005.png` **同事务、同号**——任何竞态都不可能错位（同 await 序列）。

**拒绝路径**：(a) writeStepPng 内自己 +1 维护 PNG seq map → 当 jsonl 写完后 PNG 写失败再次写时 seq 错位；(b) caller 自己维护 seq → 状态在两处，违反单一事实源；C2 `writeFailurePng` 不返回 seq 是因为没有外部 artefact 要对齐（PNG 自包含），C5 必须返回。

## 7 决策答案（含拒绝路径，每条必答）

### 决策 1：截屏来源 = `this.base.screenshot()` vs 别的方式

**答**：候选 A — **复用 `this.base.screenshot()`**（即 `SimctlDriver.screenshot()` → `client.screenshot(udid)` → simctl io tmp file → readFile）。

理由：
- `base.screenshot()` 是 Driver interface 公开方法，已在所有路径生产可用（v0.1 起 e2e 验证）
- 0 新 src 代码 / 0 dep / 0 swift 改动
- 单次 ~100-300ms 可接受（v0.5 决策日志已记 "上限 50 截图 / 默认开启 / `--trace=off` 关掉" 推 v0.5）

拒绝路径：
- 拒绝（B）"新增 runner /screen endpoint"：需 swift 改动 + 新 endpoint serialization；违反 swift 0 改动硬约束
- 拒绝（C）"复用最近一次 cached PNG（不主动截）"：cache 在哪存？需新状态；且 action 后状态变了，cache 失效；与 cold plan 字面"每个 action *后* 自动截屏"违背
- 拒绝（D）"用户 `--trace=off` 时跳过"：配置入口是 v0.5 范围；C5 范围内**无条件**截屏（cold plan 已记 v0.5 加 cap/开关）

### 决策 2：写盘命名 = `step-<NNNN>.png` vs `<NNNN>.png` vs `<NNNN>-<action>.png`

**答**：候选 A 修正 — **`step-<NNNN>.png`**（4-digit zero-pad）。

形式：`step-0001.png` / `step-0002.png` / ... / `step-0042.png`。

理由：
- `step-` 前缀分桶清晰（与 `failure-<NNNN>.png` / `<NNNN>-screenshot.png` 同前缀分桶模式）
- AI 扫目录看 prefix 即知 "this is auto trace, that is failure, that is user-asked"
- 4-digit pad 与 jsonl 行 seq 字段 1:1 对齐：jsonl `{"seq":5,...}` ↔ `step-0005.png`；AI 跨文件 join 直观
- 与 C4 plan-hot.md line 628 预案完全一致（"`<NNNN>-screenshot.png` (v0.2 C6) 与 `step-<NNNN>.png` (C5) 命名共存"）

拒绝路径：
- 拒绝（B）纯 `<NNNN>.png`：与 v0.2 C6 `<NNNN>-screenshot.png` 共目录时，sort 后 `0001-screenshot.png` 与 `0001.png` 紧邻——人扫易混；且无 `step-` 前缀难解 "这个 PNG 是 step 自动捕的"
- 拒绝（C）`<NNNN>-<action>.png` (如 `0005-tap.png`)：(i) action type 已在 jsonl 行的 `type` 字段表达，PNG 文件名重复；(ii) 长 type 字段 (`grantPermission` 14 char) 让文件名变长且 shell 命令补全不友好；(iii) 与 v0.2 C6 命名形态 `<NNNN>-screenshot.png` 倒易混淆——`<NNNN>-tap.png` 看上去也像"用户显式调用"
- 拒绝（D）`<seq>.png`（无 padding）：sort 顺序不再 lex (1, 10, 100, 11)；与 `failure-<NNNN>.png` 4-digit 不一致

### 决策 3：screenshot action 是否再写 `step-<NNNN>.png`

**答**：候选 A — **跳过**。screenshot action 仅保留 v0.2 C6 既有 `<NNNN>-screenshot.png`，**不**额外写 `step-<NNNN>.png`。

理由：
- 同一 buffer 在同目录写两遍（双名）是浪费 disk + 误导（"为何这一步有两个 PNG 文件"）
- v0.2 C6 acceptance `<NNNN>-screenshot.png` 的语义是"用户显式问 screenshot → 这是用户要的产物"；C5 step-PNG 的语义是"系统自动每步截一张观察用"。两者意图不同，文件分桶清晰
- 截屏自身是非破坏性 read，且 `<NNNN>-screenshot.png` 已是当时屏幕快照；额外写 `step-<NNNN>.png` 信息熵 = 0
- jsonl 中 type='screenshot' 行仍存在（C4 不变）；AI 看 jsonl 知道这一步是 screenshot，看目录里 `<NNNN>-screenshot.png` 知道哪个 PNG 对应——映射明确

**精确机制**：TracingDriver.screenshot() 在 C5 改造时 **不**调 captureStepPng；其他 23 mutating method 调 captureStepPng。jsonl 中 type='screenshot' 行的 `seq` 与目录里 `<NNNN>-screenshot.png` 内的 NNNN **不**必相等（两套独立计数器：`stepSeqByCase` for jsonl/step-PNG, `TracingDriver.seq` for `<NNNN>-screenshot.png`）。这是双轨延续 C4 决策 5。

拒绝路径：
- 拒绝（B）"screenshot action 也写 step-PNG（双名共存）"：违反"单一事实源"，disk 浪费；用户读 trace 看到两张相同 PNG 会疑惑
- 拒绝（C）"v0.2 C6 `<NNNN>-screenshot.png` 改名为 `step-<NNNN>.png` 统一形态"：破 v0.2 C6 acceptance gate；retrofit 推 v0.5+ Cell 统一时再做

### 决策 4：失败 action 是否也截屏

**答**：候选 A — **是，best-effort**。action throw 时 jsonl 行 ok:false 后仍尽力调 base.screenshot() + writeStepPng；screenshot 自身也 throw 时 silent 不掩盖原 action throw。

理由：
- "tap failed at step 5" → AI 最需要看的是 *"tap 失败那一瞬间屏幕长什么样"*。失败时不截屏 = 丢最关键的故障档案信息
- C2 已建立 "matcher 失败时写 failure-NNNN.png" 先例；C5 step-PNG 是"action 失败时写 step-NNNN.png" 同精神


### 决策 7：错误处理 + finally 编排 + recordStep / captureStepPng 边界

**答**：TracingDriver 23 个非-screenshot mutating wrap 升级为：

```ts
async tap(s: Selector): Promise<void> {
  const start = Date.now()
  let err: string | undefined
  try {
    await this.base.tap(s)
  } catch (e) {
    err = e instanceof Error ? e.message : String(e)
    throw e
  } finally {
    const seq = await this.recordStep('tap', { selector: s }, err === undefined, start, err)
    if (seq !== undefined) {
      await this.captureStepPng(seq)
    }
  }
}
```

新增 `private async captureStepPng(seq: number): Promise<void>`：
```ts
private async captureStepPng(seq: number): Promise<void> {
  const sink = getTraceSink()
  if (sink === undefined) return
  try {
    const png = await this.base.screenshot()
    await writeStepPng(sink, seq, png)
  } catch {
    // base.screenshot or writeStepPng failed; silent to avoid masking the
    // wrapped action's throw or polluting AI-facing stdout with trace IO noise.
  }
}
```

`recordStep` 改返回 `Promise<number | undefined>`：sink 缺失或 fs 错时返回 `undefined`，写盘成功返回 jsonl 行的 seq 值。`appendStep` 同步改返回 `Promise<number>`（返回它刚写的 seq）。

要点：
- `await this.recordStep(...)` 仍在 finally；**recordStep 完成后再调 captureStepPng**——保证 jsonl 行先落盘（即便 screenshot 抛错，jsonl 已稳）
- jsonl 与 step-PNG 写盘**串行**：appendStep → screenshot → writeStepPng。如果 screenshot 抛错，jsonl 已写完整，目录里只缺 PNG —— AI 仍能从 jsonl 行 `ok:false err:"..."` 还原状态
- recordStep 内的 fs 错（appendStep 抛错）silent + 返回 undefined → captureStepPng 跳过（因 seq undefined），保 jsonl/PNG 两路径不分裂
- screenshot 自身抛错 silent（best-effort）：不让 base.screenshot() 的偶发失败让 23 mutating wrap 看上去都 fail
- **screenshot action 的 wrap 不改**：保持 v0.2 C6 `<NNNN>-screenshot.png` 行为；不调 captureStepPng（决策 3）

拒绝路径：
- 拒绝（A）"captureStepPng 内 throw 上抛"：会让 trace IO fail 替换业务 action 的 ok 状态；违反不变量
- 拒绝（B）"recordStep 与 captureStepPng 合一为 recordStepAndShot"：错误处理边界混合（jsonl fs 错 vs screenshot 抛错），调试时难分两类故障；拆开更清晰
- 拒绝（C）"先 screenshot 后 appendStep（顺序倒）"：如果 screenshot 抛错，jsonl 行根本不写 → AI 跨 jsonl/PNG 看到"action 发生了但无记录"，比"有记录但无 PNG" 更坑
- 拒绝（D）"用 Proxy 自动 wrap"：TS 严格类型 + Driver interface 双向不兼容（C4 决策 7 同源拒绝）
- 拒绝（E）"appendStep 返回 number; recordStep 仍 void → 用 closure 状态传 seq"：状态依赖隐性，TS 严格难追；显式 number 返回更可读

```ts
  sink: MatcherTraceSink,
  seq: number,
  png: Buffer,

  return out
}
```
