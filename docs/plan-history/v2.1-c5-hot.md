# plan-hot — v2.1 到 C5:smix-server 的 valkey 集合

## 目标 checkpoint

C5:smix-server 不再连接 valkey。"哪些 sim 正在采集"这个集合由嵌入式 kevy 持有,
`redis` 依赖与 CI 的 valkey service 容器一并移除。服务端少一个必须先起来的外部进程。

## 前置条件

```bash
cargo test -p smix-store   # C1-C4 全绿
grep -c 'valkey' crates/smix-server/src/main.rs   # 迁移前的连接点存在
```

## 步骤(线性)

### S1. 集合迁到 store

**红**
- 文件:`crates/smix-server/tests/capturing_set.rs`
- 断言:
  - `add` 后 `members` 含它;`remove` 后不含
  - 同一 udid `add` 两次,`members` 只出现一次(集合语义,不是列表)
  - 空集合返回空 `Vec`,不是错误
  - 进程重开后成员仍在(落盘)
  - **顺序无关**:`members` 的断言按排序后比较,不依赖插入顺序 ——
    集合没有顺序,依赖它的测试迟早会因实现变化而假红

**绿**
- 文件:`crates/smix-server/src/capturing.rs`(取代 `valkey.rs`)
- API:`add(&Store, udid)` / `remove(&Store, udid)` / `members(&Store) -> Vec<String>`
- 关键点:
  - kevy 的 `sadd`/`srem`/`smembers` 在 `kevy_store::Store` 上(`&mut self`),
    经 `Store::with(|s| ...)` 取用 —— 需要在 smix-store 暴露一个集合访问器,
    而不是让 smix-server 直接摸 kevy(否则"唯一打开点"的纪律就破了)
  - 保持 `CAPTURING_SET` 这个 key 名不变:它是运行中系统的既有状态

### S2. 拆掉 valkey 依赖与 CI 容器

**红**
- 无新测试(拆除类改动),由既有测试与 CI 保证

**绿**
- 文件:`crates/smix-server/Cargo.toml`、`src/main.rs`、`src/state.rs`、
  `src/error.rs`、`.github/workflows/ci.yml`
- 关键点:
  - `AppState` 去掉 `valkey` 字段,改持 store
  - `Config` 去掉 `valkey_url`;若该环境变量仍被设置,**明确报告它已无效**,
    而不是静默忽略 —— 静默忽略正是本轮反复修的那种病
  - CI 的 `services: valkey` 整段删除
