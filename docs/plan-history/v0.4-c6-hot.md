## 目标 checkpoint

**C6：`.simx/trace/<case>/failure-<NNNN>.json` 文件存在且每次 matcher 失败一个 JSON 文件，文件名 4-digit pad 与同次失败的 `failure-<NNNN>.png` `<NNNN>` 字段严格相等；JSON 内容是 `ExpectationFailure.toJSON(false)` 的输出 + 一个 `screenshot_path: "failure-<NNNN>.png"` 引用字段。** 通过后世界变成：

- 任何 `simx run <file>` 跑完后，每个 case 的 `.simx/trace/<slug>/` 目录里，每次 matcher 失败都有一对 `failure-<NNNN>.png` (v0.4 C2) + `failure-<NNNN>.json` (本 C6)；NNNN 严格同号（同 `seqByCase` 序列）。
- JSON 字段 = `{ok:false, code, message, suggestions, visibleElements, selector?, hint?, screenshot_path?}`；**不含**`screenshot` (base64) 字段（决策 2：避免 JSON 巨大，PNG 已分桶落盘）。
- AI/`claude -p` 消费模式 = `cat .simx/trace/<case>/failure-0001.json` (字段密度高) + `--image .simx/trace/<case>/failure-0001.png` (视觉) ——两文件由 JSON 的 `screenshot_path` 字段桥接。这就是 v0.4 C8 dogfood 的 wire 接口。
- 多次 matcher 失败：JSON 与 PNG 共享 `seqByCase` counter，`failure-0001.{png,json}` / `failure-0002.{png,json}` 同号成对。
- screenshot 缺失 (sink 注册但 `screen.screenshot` 为 undefined) 时：仍写 JSON（含 `code/message/suggestions/visibleElements`），但**无** `screenshot_path` 字段；PNG 不落（同 C2 行为）；JSON 仍占一个 NNNN（通过 `reserveFailureSeq` 保 case 内 NNNN 连号）。
- sink 未注册 (`getTraceSink() === undefined`) 时：JSON 不落、PNG 不落（同 C2 silent no-op）；ExpectationFailure 的 in-memory `screenshot` base64 字段仍有，不退化。
- fs 错 (写 JSON 失败) 时：silent，matcher 仍 throw ExpectationFailure（与 C2 不变量同源）。
- 单测覆盖：JSON 落盘 + 字段全 / 与 PNG 同 seq / pretty 2-space indent / JSON 不含 base64 screenshot / sink 缺失 silent / fs 错 silent / PNG 缺失时 JSON 不带 screenshot_path。
- 真 dev sim e2e：与 C2 同形态故意错 selector → `.simx/trace/c6-failure-json/` 含 `failure-0001.png` + `failure-0001.json` 两文件；`jq` 断 JSON 7 字段集。

## 关键发现（基于现状代码精确引文）

### F1. `writeFailurePng` C2 形态 (trace-sink.ts line 46–60)

```ts
export async function writeFailurePng(
  sink: MatcherTraceSink,
  pngBase64: string | undefined,
): Promise<string | null> {
  if (pngBase64 === undefined || pngBase64.length === 0) return null
  const next = (seqByCase.get(sink.caseSlug) ?? 0) + 1
  seqByCase.set(sink.caseSlug, next)
  const num = String(next).padStart(4, '0')
  const dir = join(sink.traceRoot, sink.caseSlug)
  const out = join(dir, `failure-${num}.png`)
  await mkdir(dir, { recursive: true })
  const bytes = Buffer.from(pngBase64, 'base64')
  await writeFile(out, bytes)
  return out
}
```

**C6 改造**：返回类型 `Promise<string | null>` → `Promise<{path:string, seq:number} | null>`，body 末尾 `return { path: out, seq: next }`。`seqByCase` 内部 state 不变，外部多暴露 seq 数字让 caller (`matchers.ts`) 把 JSON 文件命名为同 NNNN。

**拒绝路径**（决策 5 论证）：
- 拒绝（A）"matchers.ts 自己 read `seqByCase` 状态"：跨模块读私有 module-level Map = state 双源
- 拒绝（B）"writeFailureJson 内部 +1 维护独立 seqJsonByCase"：与 PNG seq 失同步，AI 看到 `failure-0001.png` + `failure-0001.json` 同时存在但**不**必然对应同一次失败 → 错位调试
- 拒绝（C）"writeFailurePng 不变，matchers.ts 调 readdir 数 `failure-*.png` 文件数 +1"：fs IO 增加 + race 危险
- 选 = matchers 唯一依赖来源 = `writeFailurePng` 的 return 值（额外加 seq 字段是单字段非破坏性扩展）

### F2. `matchers.ts failure()` C2/C3 形态 (matchers.ts line 130–157)

```ts
private async failure(init: { code: ...; message: string }): Promise<ExpectationFailure> {
  const screen = await safeDescribe(this.handle)
  const visibleElements = screen?.elements ?? []
  const suggestions = buildSuggestions(this.handle, visibleElements)
  const failure: ConstructorParameters<typeof ExpectationFailure>[0] = {
    code: init.code,
    message: init.message,
    selector: this.handle.selector,
    visibleElements,
    suggestions,
  }
  if (screen?.screenshot) failure.screenshot = screen.screenshot
  const sink = getTraceSink()
  if (sink !== undefined && screen?.screenshot !== undefined) {
    try {
      await writeFailurePng(sink, screen.screenshot)
    } catch {
      // fs error must never mask the original matcher failure ...
    }
  }
  return new ExpectationFailure(failure)
}
```

**C6 改造**：当前 C2 写完 PNG 就丢 return；C6 在 sink 路径扩为：构造 `failureObj = new ExpectationFailure(failure)` 一次复用 → 嵌套 try (PNG 写盘 / `reserveFailureSeq` fallback / JSON 写盘) → 最终 `return failureObj`。决策 5 精确机制详 §决策 5。

## 7 决策答案（含拒绝路径，每条必答）

### 决策 1：JSON 命名 = `failure-<NNNN>.json` (与 PNG 同 seq) vs 单文件 `failure.json` overwrite vs 独立 seq

**答**：候选 A — **`failure-<NNNN>.json`，与同次失败的 `failure-<NNNN>.png` 共享 seq**。

理由：
- v1.md §B 字面 `.simx/cells/<id>/trace/<case>/{steps.jsonl, *.png, failure.json}` —— "failure.json" 是**文件族**描述（与 "*.png" 是族描述同义），不是 "literally 单文件 failure.json"；C2 决策日志已立 `failure-<NNNN>.png` 4-digit 多文件先例（C2 决策 2 "4 digit 留 soft-assert N≥2 余地"）
- 与 PNG 共享 seq = AI 拿到 `failure-0001.json` 看 `screenshot_path:"failure-0001.png"` 即直接 `--image` 喂 `claude -p`，无需查目录
- C2 既有 seqByCase counter 现成可复用，0 新状态

拒绝路径：
- 拒绝（B）"单文件 `failure.json` overwrite"：(i) 第二次 matcher 失败时丢第一次；(ii) 与 PNG 命名形态不一致反而违反"4 层信息一致性"；(iii) cold plan line 38 字面只是 v1.md "*.json" 族描述的同语义，不强制单文件
- 拒绝（C）"独立 seq (failure-NNNN-pkg.json / failure.NNNN.json 独立计数)"：与 PNG 错位 → AI 无法 `cat failure-0001.json` 后 `--image failure-0001.png` 字面对应；增第 4 个 seq counter = 状态爆炸

### 决策 2：JSON 内是否嵌 base64 screenshot

**答**：候选 B — **不嵌 base64**；JSON 内**只**含 `screenshot_path: "failure-<NNNN>.png"` 引用字段（同目录相对路径）。

理由：
- `claude -p ... --image .simx/trace/<case>/failure-0001.png` 是 claude CLI 既有 image 接口；JSON 文本 + 独立 PNG 是 AI 工具链金标准
- base64 嵌入 = JSON 文件 1.3x PNG 大小；一张 200KB PNG 变 ~270KB base64 字符串塞进 JSON = (a) `cat .json` 终端污染；(b) `jq` 解析慢
- `screenshot_path` 用**文件名而非绝对路径**：cd 到 `.simx/trace/<case>/` 后命令短；不绑定 cwd
- `ExpectationFailure.toJSON(true)` 这条路径在 MCP responses 仍保留（v0.6 用），C6 只规约 trace-disk 形态

拒绝路径：
- 拒绝（A）"includeScreenshot=true → JSON 自带 base64"：JSON 文件巨大；C8 dogfood 体验差
- 拒绝（C）"JSON 不含 screenshot 字段，PNG 路径需 caller 自己拼"：AI 需查目录拼 NNNN；信息接力断
- 拒绝（D）"JSON 含 `screenshot_path` 绝对路径"：CI / 用户机 cwd 不同；绝对路径不 portable

### 决策 3：写入层 = 扩 `trace-sink.ts` vs `matchers.ts` 直 fs.write

**答**：候选 A — **扩 `trace-sink.ts`** 加 `writeFailureJson(sink, seq, payload)`。

理由：
- C2/C4/C5 已立 "matcher / driver / cli 三方共消费写盘单点" 先例（v1.md decision log 三次重申）；C6 沿袭统一所有产物落盘语义
- `writeFailureJson` 签名与 `writeFailurePng` / `writeStepPng` 同形态；caller 不需知路径结构
- 路径 / 4-digit pad / mkdir recursive / pretty JSON 序列化 全在 trace-sink 集中

拒绝路径：
- 拒绝（B）"matchers.ts 自 `fs.writeFile`"：state 在两处，违反单一事实源
- 拒绝（C）"新文件 `failure-json-sink.ts`"：5 类 trace 产物拆五个 module = 抽象爆炸

### 决策 4：JSON schema 全字段 — 哪些必有？timestamp 加吗？

**答**：候选 = **复用 `SerializedFailure` 5 必有 + 2 可选 + C6 新加 1 可选（`screenshot_path`）；不加 timestamp**。

| 字段 | 必有? | 来源 | 决策理由 |
|---|---|---|---|
| `ok: false` | ✓ | `toJSON(false)` | wire 协议跨边界识别字段 |

```ts
export async function writeFailurePng(
  sink: MatcherTraceSink,
  pngBase64: string | undefined,
): Promise<{ path: string; seq: number } | null> {

  const next = (seqByCase.get(sink.caseSlug) ?? 0) + 1

  await writeFile(out, bytes)
  return { path: out, seq: next }
}
```

```ts
/**
 * Payload written to <traceRoot>/<caseSlug>/failure-<NNNN>.json by writeFailureJson.
 *
 * Equivalent to SerializedFailure (the wire form emitted by
 * ExpectationFailure.toJSON(false)) plus an optional screenshot_path field
 * that points at the sibling failure-<NNNN>.png. Decision 2: trace-disk JSON
 * never embeds the base64 screenshot — the PNG file is the carrier.
 */
export type FailurePayload = SerializedFailure & {
  readonly screenshot_path?: string
}

/**
 * Reserve a new failure seq for the current case without writing a file.
 * Used by matchers.ts when the screenshot is unavailable so the JSON file
 * is still numbered consistently with the case's seqByCase counter
 * (decision 5). Increments the same `seqByCase` Map that writeFailurePng
 * uses, so PNG and JSON never collide on NNNN within a case.
 */
export function reserveFailureSeq(sink: MatcherTraceSink): number {
  const next = (seqByCase.get(sink.caseSlug) ?? 0) + 1
  seqByCase.set(sink.caseSlug, next)
  return next
}

/**
 * Write the matcher-failure JSON payload to
 * `<traceRoot>/<caseSlug>/failure-<NNNN>.json`.
 *
 * `seq` must come from a prior writeFailurePng return value or
 * reserveFailureSeq() call so this JSON file and its sibling
 * failure-<NNNN>.png share the same NNNN suffix within the case. Pretty-
 * printed with 2-space indent so AI consumers can `cat` the file and feed
 * it to claude -p with the sibling PNG via --image. Callers (matchers.ts)
 * silence fs errors so trace-write failures never mask the matcher's
 * throw. Returns the absolute path written.
 */
export async function writeFailureJson(
  sink: MatcherTraceSink,
  seq: number,
  payload: FailurePayload,
): Promise<string> {
  const num = String(seq).padStart(4, '0')
  const dir = join(sink.traceRoot, sink.caseSlug)
  const out = join(dir, `failure-${num}.json`)
  await mkdir(dir, { recursive: true })
  await writeFile(out, JSON.stringify(payload, null, 2))
  return out
}
```
