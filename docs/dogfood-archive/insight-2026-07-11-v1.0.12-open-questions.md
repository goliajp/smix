## Why this file exists

The response doc (`insight-2026-07-11-post-native-fix-response.md`) proposed a systemic direction for v1.0.12-14. That direction has 8 open questions we can't settle from our side alone. This file collects them in one place with just enough context so answering each is a discrete action, not a full-context re-read.

Answering formats we'll take, in order of preference:

1. Inline reply in a `smix-feedback-2026-07-11-v1.0.12-answers.md` with the Q# tags below, one bullet per question. No prose needed — a sentence or a code fragment is fine.
2. Slack DM to `@claude` with the same tag structure.
3. Whatever's easiest — we're not gate-locking answers on format.

If any question is malformed (wrong premise, missing option, we're asking the wrong thing), please push back — the goal is design shape correctness, not fast Q&A.

## Priority tiers

- **P0 — blocks v1.0.12 design.** Cluster A / B core semantics. If we don't know these we can't RFC.
- **P1 — blocks v1.0.13 design.** Cluster C semantics. Time-shiftable if v1.0.12 lands first.
- **P2 — nice-to-have.** Improves defaults or ergonomics. We'll pick sensible defaults if silent, revisitable later.

## Cluster A — dev-fixture wipe verb (v1.0.12)

### Q1 — `insight://dev-mutate?action=reset` completion signalling [P0]

**Context.** Our `resetAppData` verb design in the response doc §Cluster A wants to fire your reset URL, then wait for it to complete before terminating the app. Without a completion signal, either we terminate too early (destroys state mid-wipe) or we sleep-then-hope (unreliable, especially under Metro cold).

**What we need to know:**

- Does the URL scheme currently signal completion? (Yes / No)
- If yes, how? Pick one or add:
  - (a) Second URL scheme fired back at smix (e.g., `smix://reset-complete?token=…`)
  - (b) Status URL smix polls (e.g., `insight://dev-mutate?action=status` → JSON)
  - (c) HTTP endpoint smix polls (e.g., `http://localhost:8081/insight-dev/reset-status`)
  - (d) Log-line pattern in the metro log (e.g., `"[insight-dev] reset-complete"`)
  - (e) IPC file at a known path (e.g., `~/Documents/insight-dev-reset-complete.marker`)
- If no signal exists today, is it easy to add on your side, or should smix do best-effort (fire URL, sleep configurable ms, then terminate)?

**Unblocks:** `resetAppData` verb shape + wait semantics.

### Q2 — reset+launch: nested or separate? [P0]

**Context.** Response doc §Cluster A showed a proposal:

```yaml
- resetAppData:
    via: url-scheme
    url: 'insight://dev-mutate?action=reset'
    waitFor: { … }
    thenLaunch: { launchArgs: [...], waitForForegroundMs: 15000 }
```

Alternative — split into two verbs, no `thenLaunch`:

```yaml
- resetAppData:
    via: url-scheme
    url: 'insight://dev-mutate?action=reset'
    waitFor: { … }
- launchApp:
    launchArgs: [...]
    waitForForegroundMs: 15000
```

**Preference (Yes / No / Something else):**
- Nested (as first shape) — 1 verb, atomic-looking, harder to interleave debug steps between reset and launch
- Separate (as second shape) — 2 verbs, matches how `clearAppData` + `launchApp` currently pair, easier to add a probe step between them
- Neither — you'd prefer another shape

**Unblocks:** yaml parser + SDK API surface for the new verb.

### Q3 — is `clearAppData` still valuable in v1.0.12+? [P1]

**Context.** If `resetAppData` covers your headline case (dev-fixture-preserving wipe), do you have a real scenario where `clearAppData` (container-wipe-everything) is still needed?

- (a) Yes, keep it — "true first-install QA" scenarios still fire it occasionally
- (b) No, deprecate it — nobody's use case survives after `resetAppData` lands
- (c) Yes but rename it to something clearer — the "clearAppData" name implies partial (which is what `resetAppData` really is); "wipeContainer" or "reinstall" better captures the semantics

**Unblocks:** deprecation policy + docs strategy for v1.0.12.

### Q4 — `clearState + clearKeychain` dialog re-check [P0-A]

**Context.** From the response doc §Direct answer: legacy `clearState` uses pre-v1.0.4 `simctl uninstall + install`, which historically triggered the "Insight quit unexpectedly" dialog. You noted you're using `clearState + clearKeychain` as a bandaid.

**What we need to know:** with the two native UAFs now fixed on your side, does the dialog:
- (a) Not appear at all (native fixes closed the underlying issue)
- (b) Appears less frequently (e.g., 1/6 launches vs previous 4/6)
- (c) Appears at same rate (native fixes were orthogonal)

**Unblocks:** whether legacy `clearState` needs backporting to v1.0.8's cooperative-terminate underneath as a quick-fix, or whether it's fine as-is.

## Cluster B — External metro log-gate (v1.0.12)

### Q5 — metro log path stability [P0]

**Context.** `smix run --metro-log <path>` design assumes the path is stable across smix's run (or at least: the file at that path is only append-truncate-safe across the run window).

Your v1.0.10 feedback mentioned `nohup bun dev > /tmp/metro.log 2>&1`. That's fine — no rotation, no truncate.

**What we need to know:**

- Do you ever rotate `/tmp/metro.log` (logrotate, size-based, etc.)? Yes / No
- Do you ever truncate it (`> metro.log`) mid-run? Yes / No / Only between runs
- Is the path stable per-checkout, per-user, or per-run? If per-run, do you need `smix run` to accept a glob (`/tmp/metro-*.log`)?

**Unblocks:** whether we need rotation-safe tail (`inotify` on the parent dir + re-open) or plain O_APPEND is enough.

### Q6 — dump `metroLogTail` size default [P2]

**Context.** Response doc proposed 200 lines default. Some batch failures generate huge JS stack traces — 200 lines might truncate the useful part.

- (a) 200 is fine, we can `--metro-log-tail-lines N` if we need more
- (b) 500 default, still configurable
- (c) Full log unless configured — smix passes the whole file (could be MB) through the dump

**Unblocks:** wire schema defaults + diagnostic JSON size envelope guarantees.

## Cluster C — reachedInteractive semantics (v1.0.13)

### Q7 — "usable" fingerprint accessibility identifiers [P1]

**Context.** `launchAppReachedInteractive` needs an `interactiveProbe.ignore` list + `minIdentifierCount` in `.smix/config.yaml`. Response doc pushed back on hard-coded `SplashScreenLogo` — we want consumer config from day one.

**What we need to know (bootstrap-scope-usable state on iOS sim, `com.focusai.app.mobile`):**

- Two-to-three ax-ids that are on-screen ONLY during unusable states (splash / dev-launcher / bundle-loading). We seed these into the default ignore list.
- Two-to-three ax-ids that appear on-screen when the app IS usable (bootstrap-scope: dev-bubble / env-switch UI / qa-bubble / any Login-screen widget). We use these as positive fingerprints for what `reachedInteractive` should look like.
- Minimum count that reliably indicates "usable, not splash-with-artifacts". Response doc guessed 3. Your call.

**Unblocks:** `.smix/config.yaml` schema + reachedInteractive default template we ship for RN/Expo consumers.

### Q8 — `waitForInteractiveMs` failure mode [P1]

**Context.** If runner polls tree during the wait window and never sees the "usable" fingerprint, what should happen?

- (a) `launchApp` returns success anyway; caller sees zero counter delta and diagnostic dump surfaces `launchAppTimedOutBeforeInteractive`. Caller decides what to do.
- (b) `launchApp` returns failure. Caller's next step is skipped and an error propagates. Consumers use this as an implicit gate.
- (c) Runner keeps polling forever until the deadline; then (a) or (b) based on a config flag.

We lean (a) for consistency with `waitForForegroundMs` semantics today.

**Unblocks:** launchApp wire response semantics + SDK behaviour.

## Meta

**We are not shipping v1.0.12 or v1.0.13 until Q1-Q4 have answers.** Everything downstream depends on them.

**Q5-Q6 (Cluster B)** we can pick sensible defaults if silent (stable path assumption + 200 lines default) and iterate — Cluster B is orthogonal enough that a v1.0.12 with Cluster B on defaults + Cluster A blocked is not what we want, but a v1.0.12 with Cluster A ready but B on defaults is fine to ship.

**Q7-Q8 (Cluster C)** don't block v1.0.12; they block v1.0.13's RFC. Fine to answer them a week or two after Q1-Q4.

**Q9 (docker testbed)** doesn't block RFC design — it blocks pre-publish gate. If it lands late we'd ship v1.0.12 on Preferences smoke (like every previous release) but that's a repeat of the anti-pattern you called out. We'd prefer to wait.

**Q10** is quality-of-life. Answer whenever.
