## 1. Root cause — code-level confirmation

Insight's hypothesis in §72-75 of the feedback is exactly what the code does. From `swift-bridge/SmixRunnerUITests/SmixRunnerUITests.swift`:

```swift
// line 716-717 — runner boot time, executed ONCE
let bundleId = TargetBundleResolver.resolve(env: ProcessInfo.processInfo.environment)
let app = XCUIApplication(bundleIdentifier: bundleId)

// ...

// line 922 — snapshotHandler closure captures `app` by reference
snapshotHandler: { scope in
  // ... uses the outer `app` — the one bound at boot ...
  try? app.snapshot()
}
```

Every subsequent `/tree` / `/find` / `/tap` / etc. call uses that same `XCUIApplication` instance. `TargetBundleResolver` reads `TEST_RUNNER_SMIX_RUNNER_TARGET_BUNDLE` env → falls back to `com.apple.Preferences` (the runner's built-in default) when unset.

**Chain of events for the insight repro**:

1. Insight team runs `smix runner up sim-insight` — no `--bundle` flag → `TargetBundleResolver` returns `com.apple.Preferences`
2. `let app = XCUIApplication(bundleIdentifier: "com.apple.Preferences")` binds forever
3. Someone taps an OS-level image preview → Preferences flashes foreground briefly
4. `xcrun simctl launch <UDID> com.focusai.app.mobile` → Insight foreground
5. `smix run --bundle-id com.focusai.app.mobile` → yaml adapter sends `/tree` requests
6. Handler uses `app` (still bound to Preferences) → XCUITest tries to snapshot Preferences (not visible) → snapshot fails → 500 `snapshot_unavailable`

The `--bundle-id` flag on `smix run` reaches the yaml adapter but stops there — it does NOT flow to the runner as a per-request annotation. Fixing this is where v0.2.1 lives.

## 2. v0.2.1 landing plan — one milestone, one commit chain

The v0.2.1 milestone is a bugfix release. No new features, no API changes visible to insight yaml authors, no wishlist items pulled in.

Milestone name: **smix v0.2.1 "runner target rebind"**. Semver patch (0.2.0 → 0.2.1) because the wire format gains an optional header only — existing clients keep working.

### Phase A — swift runner: per-request bundle-id

- **A1**. `SmixRunnerServer.SnapshotHandler` signature widens from `(_ scope: String?)` to `(_ scope: String?, _ bundleId: String?, _ activate: Bool)`. Same treatment for `TapHandler`, `FindHandler`, etc. — every handler that operates on `XCUIApplication` gains the two optional params.

- **A2**. Route handlers parse two request headers:
  - `App-Bundle-Id: <bundle>` — target bundle for THIS request (overrides the boot-time `app`)
  - `App-Activate: true|false` — if true, call `.activate()` before the snapshot; default false (keeps current behavior + protects user's foreground state)

- **A3**. In `SmixRunnerUITests.swift`, the closures resolve their own `XCUIApplication` per call:
  ```swift
  snapshotHandler: { scope, bundleId, activate in
    let target: XCUIApplication
    if let b = bundleId, b != cachedBundleId {
      target = XCUIApplication(bundleIdentifier: b)  // per-request rebind
    } else {
      target = app  // cached, same as v0.2.0 for byte-identical zero-flag path
    }
    if activate {
      target.activate()  // insight's suggestion §2 — opt-in
    }
    return try? target.snapshot()
    // ...
  }
  ```

- **A4**. Every other handler (find/tap/press/swipe/etc.) that referenced the outer `app` gets the same per-request check. Bundled patch, single file diff.

- **A5**. `cachedAppFrame = app.frame` at line 731 becomes lazy per-target: cache is a `[String: CGRect]` keyed by bundle id, populated on first hit.

### Phase B — Rust client wire

- **B1**. `smix-runner-client::RunnerClient` gains an optional context field: `pub target_bundle_id: Option<String>`. Set via `RunnerClient::with_target_bundle(bundle_id)` builder or per-call `.with_bundle_header(...)`.

- **B2**. Every request builder in the client (`find`, `tap`, `tree`, `screenshot`, ...) adds the `App-Bundle-Id: <bundle>` header when the field is Some. Existing consumers that don't set it → header absent → runner uses the boot-time `app`. Byte-compat.

- **B3**. Optional client hint `App-Activate: true` — off by default, opt-in via `RunnerClient::with_auto_activate(true)`.

### Phase C — Rust driver / SDK / CLI

- **C1**. `smix-driver::Driver` gains a `target_bundle_id: Option<String>` set at connect time (or via `App::with_bundle_id(...)`). All calls that reach the RunnerClient thread this through the header.

- **C2**. `smix-adapter-maestro::FlowArgs.bundle_id` already exists; extend `run_flow` in `entry.rs` to seed the Driver's target bundle from this value. This is the "wire the CLI `--bundle-id` all the way to the header" work.

- **C3**. Yaml `appId:` header value also seeds the target bundle (if `--bundle-id` isn't passed). This closes the "yaml says one app, CLI says another" ambiguity by making yaml the fallback and CLI the override — same precedence as v0.2.0 today.

### Phase D — verification

  1. Boot sim; ensure Preferences is foreground (`xcrun simctl launch <UDID> com.apple.Preferences`)
  2. `smix runner up` (with default bundle = Preferences) → runner binds to Preferences
  3. Launch a different app (`com.apple.MobileSafari`)
  4. Run a smix yaml with `--bundle-id com.apple.MobileSafari` — expect `/tree` succeeds (rebinds to Safari)

## 5. Wire format compatibility — insight already knows this contract

v0.2.1 is byte-compatible with v0.2.0 for any client that doesn't send the new headers:
- Client sends no `App-Bundle-Id` → runner uses boot-time `app` (v0.2.0 behavior)
- Client sends `App-Bundle-Id: com.focusai.app.mobile` → runner rebinds to Insight for this request
- Client sends `App-Bundle-Id: com.focusai.app.mobile` + `App-Activate: true` → runner rebinds AND brings to foreground

Insight's stages/perf.ts + stages/visual.ts (post-patch) will start sending the header automatically once v0.2.1 client lands — no code change needed on insight's side, just re-install smix binary.
