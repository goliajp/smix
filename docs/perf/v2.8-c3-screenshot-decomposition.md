## Measured baseline

Two capture paths compared, both measured on mini against the same booted sim.
**Path C (current)** = per-shot `xcrun simctl io <udid> screenshot <tmp>`, the body of
`DeviceControl::screenshot` (`crates/smix-simctl/src/lib.rs:1909`).
**Path D (target)** = the persistent CoreSimulator-IOSurface grab that already ships as
`smix-capture-host` (`swift-bridge/Sources/SmixCaptureHost/main.swift`), used today by the
`/live` video pipeline (`crates/smix-server/src/capture.rs:63` direct-capture mode).

### Path C — `xcrun simctl io screenshot`, controlled (mini)

Pre-Phase-A gate (methodology §9): median-of-N + sample stdev, not a single run.

| measurement | N | median ms | p95 ms | stdev ms | min–max |
|---|---|---|---|---|---|
| **A. full `simctl io screenshot`, isolated back-to-back** | 30 | **147.1** | **153.3** | 2.7 (1.8%) | 144.1–153.5 |
| A′. same, under concurrent capture load (interleaved) | 15 | 276.4 | — | — | 214.4–313.5 |
| A″. smix's OWN recorded `wall_ms` for the simctl call (subprocess ring) | — | ~270 | — | — | 189–342 |
| B. simctl process-spawn floor (`xcrun simctl help`) | 20 | 76.0 | 85.9 | 5.4 | 72.2–95.3 |
| B′. simctl connect+device-resolve floor (`getenv <udid> HOME`) | 20 | 74.3 | 77.0 | 2.2 | 71.5–77.0 |
| C. `xcrun` tool resolve (`xcrun --find simctl`) | 20 | 3.8 | 4.7 | 0.4 | 3.5–5.0 |

**Premise re-measured (C2 lesson ①).** The brief's "~187–286 ms rough probe" is real but
**load-dependent**: isolated the subprocess is **147 ms p95 153 ms**; under concurrent
capture pressure it rises to 276 ms (214–313), and smix's own ring recorded 189–342 ms. The
spread is not smix-side variance — it is CoreSimulator's capture service (`SimRenderServer`,
`com.apple.display.captureservice`) slowing under back-to-back load, which is exactly the
pressure the pacer exists to bound. The load-bearing decomposition uses the clean isolated
147 ms; the tail is the same stages stretched by capture-service contention, not a new stage.

### Path D — persistent IOSurface grab (mini)

Measured with a standalone Swift harness that reuses `SmixCaptureHost`'s `resolveSurface`
(dlopen CoreSimulator → `SimServiceContext` → `defaultDeviceSet` → device `io.ioPorts` →
`descriptor.framebufferSurface`), then times `IOSurfaceLock` + full 12.6 MB row-stripped
`memcpy` + `IOSurfaceUnlock`:

| measurement | N | median ms | p95 ms | min–max |
|---|---|---|---|---|
| **D1. per-frame grab (surface already resolved)** | 30 | **0.29** | **0.30** | 0.28–0.30 |
| D2. surface resolve (one-time, amortized) | 1 | 57.7 | — | — |
| D3. ImageIO PNG encode (12.6 MB BGRA → 2.88 MB PNG, in-process) | 20 | 65.7 | 67.2 | 64.7–67.4 |
| D4. smix startup (`smix --version`) | 15 | 9.2 | — | 4.8–14.1 |

### smix-side post-processing (Path C), measured

| stage | N | median ms | p95 ms |
|---|---|---|---|
| `std::fs::read` of the 2.88 MB tmp PNG | 30 | 0.08 | 0.80 |
| `ensure_srgb_chunk` splice (2× ~2.88 MB copy) | 30 | 0.09 | 0.09 |
| `pacer.compute_wait` (arithmetic; elapsed 147 ms ≥ 100 ms floor) | — | ~0 | 0 |

**Gap.** Path C isolated 147 ms vs Path D diff-loop **0.3 ms** = **490×**. Path C vs Path D
file-save (0.3 ms grab + 66 ms encode = **~66 ms**) = **2.2×**. Both Path-D variants land
**< 100 ms p95**. The gap is far beyond the 1.5× idiomatic bound — it is not a platform/
simulator ceiling, it is the per-shot process-spawn + capture-service round-trip that Path D
skips by reading the framebuffer surface directly.

## Stages (side-by-side, ≥18)

Legend: **C** = current per-shot `simctl io screenshot` path; **D** = persistent IOSurface
path. µs/ms per the measured splits + cost table. Δ is C − D.

### S01 — capture entry (`screenshot()` / consumer call)
- C: `crates/smix-simctl/src/lib.rs:1909` `DeviceControl::screenshot(udid)` async entry. atomic: 1 fn call. **~0 ms**.
- D: same public entry; body swapped to grab from a cached surface handle. **~0 ms**.
- Δ ≈ 0. Cause: shared entry. Attack: none.

### S02 — pacer gate (`compute_wait`)
- C: `lib.rs:1911-1919` locks the pacer mutex, `screenshot_pacer.rs:102` `compute_wait`. On a warm loop, elapsed since last call (≥147 ms) ≥ `min_interval` 100 ms floor → returns `Duration::ZERO`. atomic: 1 mutex + arithmetic. **~0 ms** (measured/derived).
- D: pacer's crash-guard rationale (capture-service `brk 1`) does **not** apply to a direct IOSurface read — S2 must revisit the floor, else a 0.3 ms grab would be gated to 100 ms. **~0 ms** (with floor revisited).
- Δ ≈ 0 today. Cause: floor is below the current 147 ms cadence. Attack: none for C; S2 design note for D.

### S03 — tmp path format
- C: `lib.rs:1925-1927` `temp_dir().join(format!("smix-screenshot-{udid}-{pid}.png"))`. atomic: 1 alloc. **<0.01 ms**.
- D: none — no tmp file. **0 ms**.
- Δ ~0. Cause: C round-trips through disk. Attack: subsumed by S14.

### S04 — spawn `xcrun` (fork/exec)
- C: `lib.rs:1042` `Command::new("xcrun")` → `cmd.output().await` (`lib.rs:1051`). fork/exec a new process. atomic: 1 fork/exec. Part of the spawn floor. **~5 ms**.
- D: none. **0 ms**.
- Δ ~5 ms. Cause: per-shot process creation. **Attack #1.**

### S05 — `xcrun` tool resolve
- C: `xcrun` resolves `simctl`'s path via its tool cache. MEASURED (`xcrun --find simctl`) **3.8 ms** (p95 4.7). atomic: cache stat. **~3.8 ms**.
- D: none. **0 ms**.
- Δ ~3.8 ms. Cause: `xcrun` indirection every shot. **Attack #1.**

### S06 — `simctl` binary load + dyld (frameworks)
- C: exec `simctl`, dyld maps `simctl` + linked CoreSimulator/Foundation. Dominant half of the spawn floor: B (`help`) 76 ms and B′ (`getenv`, which also connects+resolves) 74 ms are ~equal → the connect is cheap, **the spawn+dyld is the floor**. atomic: dyld page-ins. **~70 ms** (76 floor − 3.8 xcrun, minus the ~2 ms exec in S04). 
- D: none — surface resolved once (D2 57.7 ms), never re-spawned. **0 ms** per shot.
- Δ **~70 ms** (47.6% of C). Cause: cold CoreSimulator-CLI launch per shot. **Attack #1 (the prize).**

### S07 — CoreSimulatorService connect
- C: `simctl` opens the CoreSimulatorService XPC channel. Folded into the B′/B floor (getenv ≈ help ⇒ connect is not separately expensive on a warm service). **~1–2 ms**.
- D: none — `SimServiceContext.sharedServiceContextForDeveloperDir:` resolved once at D2. **0 ms** per shot.
- Δ ~1–2 ms. Cause: per-shot XPC. Attack: folded into #1.

### S08 — device resolution
- C: `simctl` resolves the UDID → `SimDevice`. Inside the B′ floor. **~1 ms**.
- D: resolved once at D2 (`devices.first(where UDID==)`). **0 ms** per shot.
- Δ ~1 ms. Cause: per-shot lookup. Attack: folded into #1.

### S09 — capture-service request (framebuffer acquire)
- C: `simctl io ... screenshot` asks `SimRenderServer` / `com.apple.display.captureservice` for the display framebuffer. This is the stage that **slows under load** (A′ 276 ms, A″ up to 342 ms) — the exact `brk 1` pressure point the pacer guards (`screenshot_pacer.rs:3-6`). Isolated it is small. **~2–5 ms isolated, tail-heavy under load**.
- D: `IOSurfaceLock(surface,[.readOnly])` on the already-held `framebufferSurface`. No capture service. **~0 ms**.
- Δ small isolated / **the whole tail** under load. Cause: C routes every shot through the capture service; D reads the surface memory directly. **Attack #1.**

### S10 — framebuffer pixel grab
- C: capture service copies the framebuffer into `simctl`'s address space (internal, not separately probed; bounded by the A envelope). **~1 ms**.
- D: `memcpy` 12.6 MB row-stripped out of the locked IOSurface. MEASURED **D1 = 0.29 ms** (p95 0.30). atomic: 2622 row copies. **~0.3 ms**.
- Δ ~0. Cause: same pixels, different transport. Attack: none — the grab is essentially free either way; this is the proof the bottleneck is *not* the pixels.

### S11 — PNG encode
- C: `simctl` encodes the 12.6 MB frame → 2.88 MB PNG (ImageIO). Not separately probed inside simctl, but the equivalent in-process encode MEASURED **D3 = 65.7 ms** (p95 67.2), output 2,883,106 B ≈ simctl's 2,883,003 B → same encoder. **~66 ms** (44.9% of C).
- D (file-save): the same 66 ms, but **in-process** (no subprocess). D (diff-loop): **skipped entirely** — consumers decode PNG→grayscale immediately (see Runtime-count), so a raw BGRA frame is dhashed directly. **0–66 ms**.
- Δ 0 (file-save) to 66 ms (diff-loop skips it). Cause: C always PNG-encodes even when the consumer throws the encoding away. **Attack #2.**

### S12 — PNG write to disk (simctl side)
- C: `simctl` writes 2.88 MB to the tmp file. **~1–2 ms**.
- D: none (bytes handed back in memory). **0 ms**.
- Δ ~1–2 ms. Cause: disk round-trip. Attack: folded into #1.

### S13 — `xcrun`/`simctl` process teardown
- C: process exit, dyld unmap, wait4 reap. Part of the `cmd.output().await` envelope. **~1–2 ms**.
- D: none. **0 ms**.
- Δ ~1–2 ms. Cause: per-shot teardown. Attack: folded into #1.

### S14 — smix reads the tmp PNG back
- C: `lib.rs:1929-1934` `std::fs::read(&tmp)`. MEASURED **0.08 ms** median (p95 0.80). atomic: 1 open+read 2.88 MB. **~0.5 ms** (cold-syscall estimate; warm 0.08).
- D: none — bytes already in memory. **0 ms**.
- Δ ~0.5 ms. Cause: C's disk round-trip. Attack: folded into #1.

### S15 — smix length sanity check
- C: `lib.rs:1948-1953` `if bytes.len() < 8`. atomic: 1 compare. **<0.001 ms**.
- D: same guard on the encoded/handed bytes. **~0 ms**.
- Δ ≈ 0. Cause: identical. Attack: none.

### S16 — `ensure_srgb_chunk` scan
- C: `lib.rs:2003` → `scan_png_chunks` (`lib.rs:2025`) walks chunk headers until the first `IDAT` (IHDR + a handful of chunks, **not** the whole file). On iOS 26.5 the PNG lacks an `sRGB` chunk (`lib.rs:1977`), so `has_srgb=false`. atomic: ~4 chunk-header reads. **<0.01 ms**.
- D: an ImageIO-encoded PNG already carries sRGB → scan finds it → no-op; or diff-loop skips PNG entirely. **~0 ms**.
- Δ ≈ 0. Cause: cheap header walk. Attack: none.

### S17 — `ensure_srgb_chunk` splice
- C: `lib.rs:2014-2018` `Vec::with_capacity(len+13)` + 2× `extend_from_slice` (~2.88 MB copied). MEASURED **0.09 ms**. atomic: 1 alloc + 2 memcpy. **~0.1 ms**.
- D: no splice (ImageIO emits sRGB) / diff-loop has no PNG. **~0 ms**.
- Δ ~0.1 ms. Cause: C fixes simctl's missing sRGB chunk. Attack: none (sub-0.1 ms; and D removes the need — ImageIO writes sRGB natively).

### S18 — smix removes tmp + records pacer
- C: `lib.rs:1935` `remove_file` (~0.1 ms) + `lib.rs:1944` `pacer.record(wall,failed)` (mutex + VecDeque push, ~0 ms). **~0.1 ms**.
- D: no tmp; pacer record retained if a rate cap is still wanted (much lower floor). **~0 ms**.
- Δ ~0.1 ms. Cause: C's disk cleanup. Attack: folded into #1.

### S19 — CLI-wrapper overhead (per-invocation, NOT per-shot)
- C: `smix sim screenshot` as a fresh CLI process measured **424 ms median / 449 p95** e2e (N=30). That is smix startup (S04 floor ~9 ms) + the subprocess (147–342 ms) + the fresh-process CoreSimulator warm-up tax. A **long-running** consumer (maestro runtime loop, MCP server, SDK) pays this **once**, then loops `screenshot()` at the S01–S18 per-shot cost. The 424 ms is a CLI artifact, not the per-capture number the <100 ms target governs.
- D: a long-running consumer holding a resolved surface loops at D1 0.3 ms (diff) / ~66 ms (file). **≤66 ms**.
- Δ: CLI framing inflates the headline; the governed number is the library `screenshot()` path. Attack: not on the per-shot budget.

### S20 — consumer decode (why the diff-loop path can drop PNG)
- C: `crates/smix-adapter-maestro/src/runtime.rs:1430-1432` calls `self.app.screenshot()` **twice per loop iteration**, then `png_gray.rs:51 decode_gray` decodes each PNG back to grayscale (`png_gray.rs:1` "PNG → grayscale sampling"). The PNG that simctl spent 66 ms encoding is decoded and discarded.
- D: hand the consumer the raw BGRA frame; dhash/quiescence sample grayscale directly — no encode, no decode.
- Δ: eliminates a 66 ms encode **and** a decode per shot for the dominant diff-loop consumers. Cause: format mismatch between capture (PNG) and consumption (grayscale). **Attack #2.**

## Budget validation

Path C, isolated median **147.1 ms**, reconciled against the measured stage splits:

```
S04 spawn xcrun (fork/exec)                            ~5.0 ms
S05 xcrun tool resolve                       (measured) 3.8 ms
S06 simctl binary load + dyld frameworks   (measured) ~70.0 ms   ← 47.6%
S07+S08 CoreSim connect + device resolve              ~2.0 ms
S09+S10 capture-service request + grab                ~3.0 ms
S11 PNG encode                              (measured) 66.0 ms   ← 44.9%
S12 PNG write to disk (simctl)                        ~1.5 ms
S13 process teardown                                  ~1.5 ms
---------------------------------------------------------------
subprocess subtotal                                  ~152.8 ms
measured isolated median                              147.1 ms
delta                                                  +5.7 ms (3.9% over)
```

Δ = **+3.9%**, **within the ±20% hard constraint** — no missing stage. (The two measured
anchors, spawn floor 74–76 ms and PNG encode 66 ms, alone account for **95%** of the 147 ms;
the ±4% residual is spawn/exec/teardown/capture-service estimated from the cost table under
the measured envelope.)

smix-side additions on top of the subprocess (S02+S14–S18): fs::read ~0.5 + srgb splice ~0.1
+ remove ~0.1 + pacer ~0 = **~0.7 ms = 0.5% of 147 ms**. The pacer floor adds **0 ms** at the
current cadence (S02).

Path D target budget: diff-loop = S01–S02 (~0) + D1 grab **0.3 ms** + dhash decode-free; 
file-save = D1 0.3 ms + D3 encode **66 ms** = **~66 ms p95**. Both < 100 ms. Reconciles
trivially against the measured D1/D3 primitives.

## Runtime-count verification (methodology §2, the luna lesson)

Source-read is necessary, NOT sufficient. Three load-bearing claims, each verified by running
the actual workload on mini:

1. **"The framebuffer grab is not the bottleneck; the per-shot spawn is."**
   The isolated subprocess is 147 ms, but the spawn floor (`xcrun simctl help` = 76 ms,
   `getenv` = 74 ms) and the in-process PNG encode (66 ms) together = **95%** of it, while the
   actual pixel grab (D1) is **0.29 ms**. `help` (no connect) ≈ `getenv` (connects+resolves) ⇒
   the connect is cheap; **spawn+dyld is the tax.** Measured, not reasoned.

2. **"A persistent IOSurface grab is real and fast."**
   The standalone harness resolved `framebufferSurface` (57.7 ms once) and then grabbed a full
   1206×2622 12.6 MB frame in **0.29 ms median, 0.30 ms p95, stdev 0.006 ms** over 30 samples.
   This is the same resolution `smix-capture-host` performs today for `/live`
   (`capture.rs:63` "Direct = smix-capture-host … streaming raw BGRA at 30fps from
   CoreSimulator's IOSurface"). The fast path is shipping code, not a hypothesis.

3. **"The dominant consumers decode the PNG straight back to grayscale."**
   `runtime.rs:1430-1432` (waitForAnimationToEnd / quiescence) calls `screenshot()` twice per
   loop iteration; `png_gray.rs:51 decode_gray` decodes each PNG to grayscale. The 66 ms encode
   is provably thrown away for the diff-loop path — so Path D can hand raw BGRA and skip both
   the encode and the decode. Verified by reading the live call sites, not assumed.

The load-sensitivity (147 → 276–342 ms) was also re-measured, not accepted from the rough
probe (C2 lesson ①): the tail is capture-service contention, the same stage S09 stretched.

Attacks #1+#2 together turn the per-shot capture from **147–342 ms** into **~0.3 ms**
(diff-loop) / **~66 ms** (file-save), a **2.2×–490× win**, and keep the per-shot `simctl io`

double-digit-pp gate (spawn 47.6%, encode 44.9%); smix-side polish (srgb/pacer/fs, 0.5%) does
**not** clear it and is correctly **not** an attack — the lever is the capture path, which smix
already owns and ships.

## Mechanism summary (for S2)

- Cache the CoreSimulator `framebufferSurface` per booted UDID inside `smix-simctl`
  `DeviceControl` (resolve once via the `SmixCaptureHost` selectors, keep the `IOSurface`).
- `screenshot()` locks + copies the 12.6 MB frame in ~0.3 ms; for file-save consumers,
  ImageIO-encode in-process (~66 ms, emits sRGB natively → `ensure_srgb_chunk` becomes a no-op);
  for diff-loop consumers, return raw BGRA and dhash it directly (skip encode + decode).
- Fall back to the existing `xcrun simctl io screenshot` path (byte-identical) when the surface
  is unresolvable (framework layout change, sim not fully booted) — preserving correctness.
- Revisit the pacer floor for the direct path (it doesn't touch `com.apple.display.captureservice`).

Target p95: diff-loop ~0.3 ms, file-save ~66 ms — **both < 100 ms**, achieved by swapping the
capture transport smix already ships for `/live`, not by shaving the 0.5% smix-side overhead.

Verdict: feasible
