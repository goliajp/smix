## Measured baseline

Two paths compared. "Us / current" = today's `smix runner cycle` = `down()` (SIGINT
xcodebuild + wait) then `up()` (respawn `xcodebuild test-without-building`). "Reference /
target" = the in-process path: bounce FlyingFox inside the surviving `test_runForever` +
rebind XCUIApplication via the existing `resolveApp` mechanism.

### Current path — `smix runner cycle` warm, median-of-3 (mini, per-line epoch-ms probes)

| run | total ms |
|---|---|
| 1 | 36262 |
| 2 | 31469 |
| 3 | 36020 |
| **median** | **36020** |
| mean | 34584 |
| sample stdev | ~2700 (≈7.5% of median) |

**PREMISE REFUTED.** The C2 task brief and the CLI banner both say "warm rebuild ~3 s".
The `~3 s` figure is only the xcodebuild *compile* step that `test-without-building`
skips — it is **not** the cycle wall time. Measured warm cycle = **~36 s**, ~12× the stated
premise. The `~3 s` number never included the down-phase SIGINT teardown (~24 s) nor the
XCUITest-host boot inside the respawn (~10 s). Every downstream estimate in the brief that
leaned on "3 s warm" is off by an order of magnitude. (Source-read of `runner.rs:744-748`
shows the banner literally prints "warm rebuild ~3 s expected" — it is a compile-time hint,
mis-read as cycle time.)

it is the xcodebuild spawn + graceful-teardown tax, which the in-process path skips entirely.

## Stages (side-by-side, ≥18)

Legend: **C** = current xcodebuild-spawn path, **T** = in-process target path. µs/ms per the
cost table + measured splits. Δ is C − T.

### S01 — CLI entry + `cycle()` dispatch
- C: `runner.rs:994` `cycle()` — `read_state` (one file read) + kevy AOF replay (workspace side-effect) + arg parse. atomic: 1 file read, ~30 AOF cmds. **~110 ms**.
- T: `runner.rs` `cycle()` → `try_soft_cycle(port)` — same `read_state` + a `/health` reachability probe (1 loopback RTT ~1.5 ms). **~112 ms**.
- Δ ≈ 0. Cause: shared prologue. Attack candidate: none (not on the gap).

### S02 — supervisor-teardown check
- C: `runner.rs:904-919` — `pid_command(sup_pid)` (`ps` fork) when a supervisor pid is recorded; skipped here (none). atomic: 0-1 `ps`. **~0-30 ms**.
- T: unchanged (soft-cycle keeps the same host, supervisor stays attached). **~0 ms**.
- Δ ≈ 0. Cause: identical. Attack candidate: none.

### S03 — locate the runner process
- C: `runner.rs:920` `pid_command(st.pid)` — one `ps` to confirm the pid is xcodebuild. **~30 ms**.
- T: none — soft-cycle never needs the OS pid; it talks to the live server. **~0 ms**.
- Δ ~30 ms. Cause: C addresses the process, T addresses the in-process server. Attack: folded into S05.

### S04 — deliver the teardown intent
- C: `runner.rs:923` `signal(st.pid,"-INT")` — SIGINT to the xcodebuild process group. atomic: 1 `kill(2)`. **<1 ms**.
- T: `SmixRunnerServer.swift` (new) `restartSignal.fire()` — continuation resume on the in-process `RestartSignal`, distinct from `ShutdownSignal`. atomic: 1 continuation. **<1 ms**.
- Δ ≈ 0 (the *delivery* is cheap in both). Cause: same intent, different transport. Attack: none here; the cost is what the intent *triggers* (S05).

### S05 — teardown execution (THE dominant current cost)
- C: xcodebuild forwards cancellation to **testmanagerd**, which cleanly cancels the XCUITest session: `server.run()` throws (socket-closed), `runForever` swallows it (`SmixRunnerServer.swift:2023-2029`), `test_runForever` returns, the XCTest host process winds down and **exits**. Polled at `runner.rs:925` every 500 ms until `pid_command` reports gone. MEASURED **23609 ms** median (65.5% of cycle).
- T: `server.stop(timeout:0)` (`HTTPServer.swift:136-144`) — close the listening socket, drain 0 in-flight connections. The host process **does not exit**; `test_runForever` stays suspended. atomic: 1 `close(2)`. **~2 ms**.
- Δ **~23607 ms**. Cause: C tears down the entire XCTest host + testmanagerd session; T only closes a socket. **Attack #1 (see Top-N).**

### S06 — down health-settle
- C: `runner.rs:964-969` — poll `/health` at 500 ms until it stops answering (confirms socket closed). **~147 ms**.
- T: not applicable — the server is deliberately kept, only re-bound. **~0 ms**.
- Δ ~147 ms. Cause: C waits for the port to go quiet. Attack: folded into S05 elimination.

### S07 — up: resolve project + prepare log
- C: `runner.rs:679-687` — `resolve_runner_project` (path walk), `create_dir_all(.smix/runner)`, create + clone log file handle. atomic: few stat/open. **~60 ms**.
- T: none. **~0 ms**.
- Δ ~60 ms. Cause: C is starting a brand-new xcodebuild; T reuses the live one. Attack: folded into S09.

### S08 — up: spawn xcodebuild
- C: `runner.rs:689-706` `Command::new("xcodebuild").args(xcodebuild_argv(...))` (`runner.rs:233`) — fork/exec a new process group. atomic: 1 fork/exec. **~49 ms**.
- T: none. **~0 ms**.
- Δ ~49 ms. Cause: process creation. Attack: folded into S09.

### S09 — up: xcodebuild loads bundle + connects testmanagerd
- C: `test-without-building` skips compile but still: loads `SmixRunner.xctest`, negotiates with testmanagerd, installs/launches the XCUITest **host** app on the sim. Not separately timestamped; part of the measured 10086 ms respawn window. Est **~4000-6000 ms**.
- T: none. **~0 ms**.
- Δ ~5000 ms. Cause: full XCUITest-host cold attach on every cycle. **Attack #2 (see Top-N).**

### S10 — up: XCUITest host process launch + dyld + swizzle `+load`
- C: `SmixA11ySwizzle.m` `+load` at dyld stage (`SmixRunnerUITests.swift:878-884`) + Swift runtime init before `test_runForever` entry. Part of respawn window. Est **~1000-2000 ms**.
- T: none — swizzle already installed in the surviving host. **~0 ms**.
- Δ ~1500 ms. Cause: host re-init. Attack: folded into Attack #2.

### S11 — up: `test_runForever` entry + `app.launch()`
- C: `SmixRunnerUITests.swift:918-921` — `LaunchModeResolver` → `app.launch()` (fresh app boot) or `.activate()`. A fresh Preferences launch is the same class of op measured at **2884 ms** by `/session/relaunch-app` (terminate+launch). Part of respawn window.
- T: the app rebind is done in-process via `resolveApp`/`/soft-cycle`, either **activate** (~300-500 ms) or the same **2884 ms** full relaunch — but it is the *only* significant target cost, not stacked on top of a 33 s teardown+respawn.
- Δ: the launch itself is comparable; the surrounding teardown+host-boot is what C pays and T skips. Cause: see S05/S09. Attack: none on the launch primitive itself.

### S12 — up: first `app.frame` snapshot
- C: `SmixRunnerUITests.swift:933` `app.frame` — light XCUI snapshot, source comment "~50-150ms". **~100 ms**.
- T: same one-time snapshot after rebind. **~100 ms**.
- Δ ≈ 0. Cause: identical primitive. Attack: none.

### S13 — up: FlyingFox `makeServer` + bind
- C: `SmixRunnerServer.swift:862-866` `HTTPServer(address:)` + `makeSocketAndListen` (`HTTPServer.swift:146-164`) — socket/bind/listen on a fresh host. **~2 ms**.
- T: `server.run()` re-entered on the SAME actor after stop — `preparePoolAndSocket` → `makeSocketAndListen` with `SO_REUSEADDR` (`HTTPServer.swift:154`). **~2 ms**.
- Δ ≈ 0. Cause: same bind cost. Attack: none (bind is not the gap).

### S14 — up: route registration
- C: `SmixRunnerServer.swift:1233-2018` — `appendRoute` × ~30 on a fresh server. atomic: ~30 dictionary inserts. **~1 ms**.
- T: **0** — routes live in the `handlers` actor property (`HTTPServer.swift:41`), untouched by `stop()`; a re-`run()` serves them unchanged. **0 ms**.
- Δ ~1 ms. Cause: T reuses the registered handler table. Attack: none (sub-ms).

### S15 — up: `server.run()` accept loop online
- C: `SmixRunnerServer.swift:2042` `server.run()` in the task group — pool prepare + accept loop start. **~2 ms**.
- T: identical re-`run()` in the restart-loop. Proven re-runnable (S17 evidence). **~2 ms**.
- Δ ≈ 0. Cause: same. Attack: none.

### S16 — up: CLI observes first `/health` 200
- C: `runner.rs:769` poll every **2 s** → up to 2000 ms quantization slack between server-ready and CLI-observed. Contributes the bulk of the ~1959 ms budget residual. **~1000 ms mean slack**.
- T: soft-cycle response *is* the readiness signal (no external 2 s poll); `/health` RTT ~1.5 ms. **~1.5 ms**.
- Δ ~1000 ms. Cause: C's coarse readiness poll. Attack candidate: not needed once S05/S09 are gone, but tightening the up-poll cadence is an independent minor win for the hard-fallback path.

### S17 — FlyingFox bounce feasibility (structural evidence stage)
- C: n/a — C never bounces; it always re-spawns.
- T: `HTTPServer.run()` guards `state == nil` (`HTTPServer.swift:93`); `stop()` resets `state = nil` (`HTTPServer.swift:138`); `makeSocketAndListen` sets `SO_REUSEADDR` (`HTTPServer.swift:154`); routes persist in `handlers` (`HTTPServer.swift:41`). **Runtime-verified** by FlyingFox's own upstream test `restarts_AfterStopped()` (`FlyingFox/Tests/HTTPServerTests.swift:106-115`): start → stop → start same instance, asserts `throws: Never`.
- Δ: this stage is the crux of the verdict, not a time cost. Cause: FlyingFox explicitly supports run→stop→run. Attack: this is what makes Attack #1/#2 possible.

### S18 — XCUIApplication in-process rebind feasibility (runtime-verified)
- C: n/a — C gets a fresh app from the respawned host.
- T: `resolveApp` (`SmixRunnerUITests.swift:1120-1150`) already rebinds XCUIApplication off the session table without ending the test; `/session/relaunch-app` (`SmixRunnerUITests.swift:2672-2690`) does `entry.app.terminate()+launch()` on main. **Runtime-verified on mini** (see Runtime-count verification): median **2884 ms**, xcodebuild pid **unchanged**, `/health` **200 after each** → `server.run()` never returned.
- Δ: proves the app-rebind half already ships in-process. Cause: session table lives in surviving host memory. Attack: reuse this exact mechanism inside `/soft-cycle`.

### S19 — cycle dispatch + hard fallback (recoverable vs unrecoverable)
- C: always `down()`+`up()`.
- T: `cycle()` tries `/soft-cycle` when `/health` is reachable; on connect-fail or host-dead markers, falls back to the byte-identical `down()`+`up()`. Recoverable subset = host alive + reachable; unrecoverable = `** TEST INTERRUPTED **` / `SchemeActionResultOperation started unexpectedly` (`runner.rs:1118-1121`) or wedged-unreachable server. **~0 ms decision cost** (1 `/health` probe already counted in S01).
- Δ: preserves N=1 contract. Cause: additive fast-path. Attack: the dispatch itself.

## Budget validation

Median-of-3 stage sum vs measured median total:

```
CLI prologue (S01-S03)                 110 ms
down SIGINT-wait (S05)               23609 ms
down health-settle (S06)               147 ms
up spawn overhead (S07-S08)            109 ms
up respawn→first /health (S09-S15)   10086 ms   (measured as one window)
-------------------------------------------------
subtotal                             34061 ms
measured median total                36020 ms
residual (S16 2 s up-poll + 500 ms down-poll quantization)  1959 ms  (5.4%)
```

Δ between explained subtotal and measured total = **1959 ms = 5.4% under**, attributed to the
coarse readiness/liveness poll cadence (S16). **Within the ±20% hard constraint.** No missing
stage. (The respawn window S09-S15 is measured as a single 10086 ms interval; its internal
sub-splits are estimated from the cost table because they occur inside xcodebuild/testmanagerd
where no per-stage probe is available — but they sum under the measured envelope, so the
envelope, not the sub-splits, is the load-bearing number.)

Target-path budget: activate path ~500 ms, full-relaunch path ~2884 ms (the app rebind is the
only non-trivial term; everything else is ≤ ~5 ms). Reconciles trivially against the measured
`/session/relaunch-app` = 2884 ms primitive.

## Runtime-count verification (methodology §2, the luna lesson)

Source-read is necessary, NOT sufficient. Two load-bearing claims, both verified by running the
actual workload on mini:

1. **"XCUIApplication rebind is already in-process; `server.run()` does not return."**
   Measured `/session/relaunch-app` (open a session, relaunch ×3):
   - internal `wallMs`: 2884 / 2891 / 2877 (median **2884 ms**, stdev ~7 ms)
   - `curl time_total`: 2.887 / 2.894 / 2.881 s (matches internal wallMs → no wire overhead)
   - `/health` immediately after each: **200 / 200 / 200** → server still serving → `server.run()` did **not** return
   - xcodebuild pid before **66566**, after **66566** → **HOST_SURVIVED=yes**, no respawn
   Verdict: the app-rebind half of an in-process cycle is real and ships today.

2. **"FlyingFox can be bounced (stop → run) without ending `test_runForever`."**
   Not a device counter but a runtime-verified library contract: FlyingFox ships a passing test
   `restarts_AfterStopped()` (`HTTPServerTests.swift:106-115`) that starts a server, stops it,
   and starts the **same instance** again asserting no throw. Backed by source: `run()` guards
   `state == nil` (line 93), `stop()` sets `state = nil` (line 138), `SO_REUSEADDR` on rebind
   (line 154), routes retained in `handlers` (line 41). The bounce is a library-supported
   operation, not a hypothesis.

Neither claim rests on source-reading alone.

## Top-N actionable attacks

Pre-Phase-B gate (methodology §9): Top-1 target must be ≥ double-digit-pp of measured cycle
self-time. down SIGINT-wait = **65.5%**, up respawn = **28.0%** — both clear it by a wide margin.
The combined soft-cycle attacks **93.5%** of cycle self-time.

| # | File:line | Concrete change | Gain | Semantic class | Blast radius |
|---|---|---|---|---|---|
| 1 | `SmixRunnerServer.swift:2039-2062` (runForever) + new `RestartSignal` | Wrap `server.run()` in a `while` restart-loop; add a `RestartSignal` distinct from `ShutdownSignal`. Stop-observer awaits both: shutdown → `stop()` + break loop → return (exit 0, unchanged); restart → `stop(timeout:0)` → loop continues → `server.run()` again (state==nil, SO_REUSEADDR, routes persist). Eliminates the ~23.6 s down SIGINT-wait because the host is never torn down. | **~23600 ms** (65.5%) | additive: new signal + loop; shutdown path byte-identical | runForever body + 1 new signal type; requires bench validation on device |
| 2 | `SmixRunnerUITests.swift` (new `POST /soft-cycle`) + `runner.rs:994` `cycle()` | New additive route: fire `RestartSignal`, then rebind XCUIApplication via existing `resolveApp`/session mechanism (activate for foreground-drift, or reuse relaunch for fresh-app semantics). `cycle()` tries `/soft-cycle` when `/health` reachable, else falls back to `down()+up()`. Eliminates the ~10 s xcodebuild respawn + XCUITest host boot. | **~10000 ms** (28.0%) | additive route; N=1/host-dead contract preserved via hard fallback | 1 new route + `cycle()` dispatch + `try_soft_cycle`; requires bench validation |
| 3 | `runner.rs:769` up-poll + `runner.rs:925` down-poll cadence | (Hard-fallback path only) tighten the 2 s up readiness poll and 500 ms down liveness poll so the ~1.96 s quantization residual shrinks. Independent minor win; does not touch the soft-cycle path. | ~1000-1500 ms on hard-cycle only | none (constant tuning) | 2 constants |

Attacks #1+#2 together are the "soft-cycle": they turn the recoverable cycle from ~36 s into
~500 ms (activate) / ~2.9 s (full relaunch), a **12-72× win**, and leave the xcodebuild
hard-cycle as the fallback for unrecoverable states.

**Recoverable subset** (soft-cycle applies): host process alive AND `/health` reachable —
covers the common explicit `smix runner cycle`, and the supervisor case where the server is
reachable but the app has drifted foreground/stale.

**Unrecoverable subset** (must keep xcodebuild hard-cycle): `** TEST INTERRUPTED **` /
`SchemeActionResultOperation started unexpectedly` (`runner.rs:1118-1121`) = the XCTest host
process is dead, so there is no in-process channel left; and the wedged-server case where
`/health` is unreachable (`runner.rs:1185` health-unreachable×3) so `/soft-cycle` cannot be
POSTed. In both, `cycle()` falls back to the existing `down()`+`up()` — byte-identical to
today, preserving the N=1 contract.

## Mechanism summary (for S2)

- Add `RestartSignal` alongside `ShutdownSignal` in `SmixRunnerServer.swift`.
- In `runForever` (`:2039-2062`), replace the single `withThrowingTaskGroup { run(); wait-shutdown→stop }`
  with a `while !shouldExit` loop: the stop-observer awaits *both* signals; **shutdown** sets
  `shouldExit=true` then `stop()` (→ loop breaks → `runForever` returns → `test_runForever`
  exits 0, semantics unchanged); **restart** calls `stop(timeout:0)` only (→ loop iterates →
  `server.run()` re-binds the same port on the same actor). `server.stop`'s current semantics
  (graceful-teardown) are reused as restart-not-end because after `stop()` the actor's `state`
  is nil (`HTTPServer.swift:138`) and `run()`'s `guard state == nil` (`:93`) then passes —
  exactly the path FlyingFox's `restarts_AfterStopped()` test exercises.
- Add `POST /soft-cycle` (additive) that fires the restart signal and rebinds the app via the
  already-shipping `resolveApp`/`/session/relaunch-app` machinery.
- `cycle()` (`runner.rs:994`) gains `try_soft_cycle(port)` first; `Err` ⇒ existing `down()+up()`.

Verdict: feasible
